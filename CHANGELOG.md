## [Unreleased]

### Added

- **`undo` can restore part of a refused batch** (#287): the undo of a `delete_events_batch`, `delete_reminders_batch` or `cleanup_completed_reminders` is refused whole before any write when the calendar or list of any of its items is missing or read-only (#248), and the only ways on were to wait or to give up every item with `discard_id`. With `restore_available: true` (opt-in, so the agent asks the user first), `undo` restores the items whose calendar or list is in place and puts back an entry of only the others, under the same id, as a part-way failure has been kept since #248. The answer is `success: true` with `partial: true` and `kept`, says what was restored and why the others are kept (kind of calendar or list and whether it is missing or read-only, item titles, no calendar, list or account name), and `discard_id` then drops only the kept items; a later `undo` restores them once their calendar or list is back. The lists are read once more for the split; if every destination is back the whole batch runs, if none can be restored the refusal stands. A save that fails part-way on the restored items keeps the kept items in the entry too. Without the argument nothing changes, except that the refusal now names `restore_available` when some items could be restored. The restored items leave a redo entry, as a whole batch undo does, so the next `redo` answers for them. If the only restorable item fails in a way no retry can restore, the kept items stay (they were never attempted); a calendar or list that disappears between the split and the write refuses the whole entry, nothing written. Members are restored independently, in the order a whole batch undo runs them (the reverse of the recorded order). Not run on a device: undo is stateful, so a release-gate step on the session MCP was added.
- **A re-exec says why** (#361): CheICalMCP re-executes itself when the host context lacks full Calendar and Reminders access, and only a forced re-exec printed anything, so nothing showed which host was there or what it had, and the decision holds for the life of the server. Every re-exec now writes one line to stderr before the exec, with the host and, except for `--setup`, its two statuses, and carries the reason, the statuses and the kind of host in `CHE_ICAL_MCP_DISCLAIMED`. `--print-tcc-path` reports only its own start: when it re-executed, it adds `CHE_ICAL_MCP_DISCLAIMED says this process re-executed at start (...)`, also when the re-exec had no effect. The variable is unauthenticated and its content is printed, so it holds closed-vocabulary tokens only, never a host name or path, anything this binary cannot write reads as unreadable, and the line is marked not verified. The stderr writes of the start-up switch cannot stop the exec or the start: a closed stderr or a pipe with no reader is ignored (the banner's own write is unchanged). A parent passing the variable twice can no longer get past the loop guard (`setenv` replaced only the first entry). The startup banner adds nothing, because the same start's stderr already has the line. A natural (status-driven) re-exec in server mode has still not been observed on a device; the forced path is covered by a test.
- **`complete_reminder` reports the next occurrence's relative alarms and the ones that appeared on the read-back** (#423): completing a repeating reminder that has a location trigger leaves one plain relative alarm at 0 minutes (no location, no proximity) on the next occurrence and on the completed copy. Measured on iCloud (2026-11-05, `--cli` and a long-lived stdio server): it does not appear without a location trigger, without recurrence or without a completion, and a later completion does not add another, whether the alarm is still there or was removed with `update_reminder` (three reminders, timed and date-only). It also appears on daily, monthly and yearly series, on an `end_date` or `occurrence_count` bound and on date-only reminders. This path sets only `isCompleted` and `completionDate`, in one save; EventKit or the store adds the alarm when that save rolls the reminder over, and which of the two was not told apart. After a confirmed rollover the response now carries `next_occurrence.alarms_minutes_offsets`, read after re-reading the next occurrence, and `alarms_note` when relative alarms appeared on that read that were not there before the completion. The note does not say who wrote them: the re-read runs right after the save, with no suspension point, so no other call of this server can write in between, but another process still could. When the next occurrence cannot be re-read, or is no longer the confirmed occurrence (identifier, list, source, recurrence, due date or completion state differ), `next_occurrence.alarms_read_back` is `false` with `alarms_read_back_note` and no alarms are reported. With any other `next_occurrence.status` these fields are absent. **Default, can be revisited**: nothing is written, since the alarm's purpose is unknown and removing it could delete one the user set; `update_reminder` with `alarms_minutes_offsets` removed it in the cases tried (on a date-only reminder only `[]` is accepted). Not checked: whether it fires and whether Reminders.app shows it (release gate, attended). The completed copy gets a new identifier and is not read. The #236 undo of the completion is unaffected (its post-state compares only the completion state, and a repeating reminder's completion undo is already refused by the #204 identity guard). An older `create_reminder` or `update_reminder` undo record of the same reminder, already refused because the due date moved, also lists `alarms` among the changed fields when the alarm appeared.
- **`update_reminder` changes or removes a reminder's recurrence rule** (#354): `recurrence` (the object `create_reminder` takes, without `excluded_occurrence_dates`) replaces the rule and `clear_recurrence: true` removes it, keeping the identifier, completion history, alarms and location trigger, where a delete and re-create lost them (alarms and location trigger: tested in memory and on iCloud; identifier and history: on iCloud). **Default, can be revisited**: a rule change does not move the due date. Measured on iCloud (2026-11-05): a weekly Thursday reminder changed to Friday keeps its identifier and its Thursday due, and completing it gives the next occurrence on Friday; clearing the rule keeps the due. When the due date is not on the rule's days (a weekday for every frequency, a day of the month for monthly and yearly), the response adds `recurrence_note`: whether the due was kept or given in this call, what happens after it is completed (measured for a weekly rule on one weekday with no end, expected for other rules), and `due_date` on `update_reminder` as the way to move it. The response reads back `has_recurrence`, `reminder_recurrence_rules` and `due` off the saved reminder after re-reading it; when it cannot be re-read, `recurrence_read_back` is `false` with `recurrence_read_back_note`, and nothing is reported as stored. Refused before any write, with a named message: `recurrence` with `clear_recurrence`; `recurrence` with `clear_due_date`; a rule when the reminder will have no due date (EventKit refuses a repeating reminder without one); a rule on a completed reminder (its rollover with a new rule was not measured); and `clear_due_date` on a reminder that keeps repeating, which used to fail at the save with an opaque `eventkit_error_18` (default; `clear_recurrence` with it makes the reminder one-off without a due date). The rule is written after the due date in the same save, and the #333 alarm checks still run before any write. Update-undo restores the previous rule and the #236 post-state guard compares it by value; a rule's end is now compared by day when both reminders compared are date-only, as an all-day event's is (tested in memory; on a session MCP, pending the release gate). Not checked: how Reminders.app displays the off-rule occurrence.
- **`delete_calendar` takes `require_empty`** (#328): with `require_empty: true`, a calendar that holds any event, or a reminder list that holds any reminder (completed ones included), is refused and nothing is deleted. EventKit has no query for every event of a calendar, so events are searched only about 200 years either side of now (an event outside, such as one typed with the year 0026, is not seen and is deleted with the calendar; the description says so before the call), in spans of 1459 days queried one EventKit query each (#325's cut is at 1461 days), stopping at the first span that holds any (the refusal gives a lower bound and the window); a passed check answers with `searched_from` / `searched_to`, so "empty" is never claimed outside them. A reminder list is counted whole; one whose reminders cannot be counted is refused, not taken as empty, and so is a calendar that allows neither events nor reminders. The check runs on the manager's actor and no write by this server process can land between it and the removal (a write made during the reminder fetch refuses with "try again"; the manager's store counts its own commits as they happen, so a writer that marks the store stale late is still seen); a write by another app or a sync still can, since EventKit cannot delete a calendar only if it is empty. The check reads this Mac's calendar data: an event still on the server and not yet synced down is not seen and is deleted with the calendar. `require_empty: null` and any key other than `id` and `require_empty` are refused, so a typo cannot fall back to the unchecked delete. Without `require_empty` the call is unchanged. The plugin skill tells callers to pass it.
- **Relative alarms on reminders** (#333): `create_reminder`, each row of `create_reminders_batch` and `update_reminder` accept `alarms_minutes_offsets`, minutes before the due date (positive = before, negative = after; integers from -525600 to 525600, one year), the parameter and sign of the event tools and of the read side's `minutes_before`. The stored due date can now keep its real time with an earlier notification (in the rows measured the list, and the one banner checked, showed the alarm time, see below). Only relative alarms are written: on `update_reminder` the list replaces the reminder's relative alarms and `[]` removes them; absolute-date alarms (#227) and the location trigger (#229) are not changed, unlike `update_event`, whose list replaces every alarm. A non-empty list needs a due date with a time after the call and is refused, with nothing written, when the reminder has none (the alarm would never fire) or a date-only one: EventKit stores a relative alarm on a date-only reminder and reads it back (device, 2026-11-05), but when Reminders fires it there has not been measured, so the refusal stays until it is. On a recurring reminder EventKit is expected to move the alarm with each occurrence; that is not yet checked on a device and is a step of the release gate. **What Reminders.app shows (#433, device 2026-11-05):** in the 14 rows measured, the list row showed the earliest time-based alarm, relative or absolute, not the due time, so a reminder due 15:30 with `[15]` read 15:15 and with `[-15]` read 15:45; that is a fit to those rows, not a documented rule. The stored due date is unchanged. The one notification checked (#333: due 09:54, `[2]`) came early, and its banner showed the same time as the list row, 09:52, not the due time. No second banner was seen at the due time, but the first was still on screen, so one hidden behind it cannot be excluded. An Early Reminder set in Reminders.app is different: the one made by hand read back with one absolute alarm at the due time and no alarm before it, so this server cannot write it. **Default, can be revisited**: `alarms_minutes_offsets` stays, and the tool descriptions and the response state the difference. The 14 rows were list rows of one iCloud list; the `[60]` and `[2]` rows came from an earlier disposable list (#333). Not checked: the detail panel, other devices, offsets that cross into another day (`[1440]`), when a `[-15]` alarm notifies, a past due date, a completed reminder, and whether `update_reminder` keeps an Early Reminder set in the app. Nothing is written differently for the note, so the #236 undo guard and `realign_to_due` (#235) are unaffected; an update with `alarms_minutes_offsets` now always reads the reminder back after the save, also with no due date change or with `clear_due_date`. On `create_reminder`, each batch row and `update_reminder`, when that re-read fails, or a create's `store_differs` lists `alarm count`, `alarms_minutes_offsets` is left out and `alarms_read_back` is `false` with `alarms_read_back_note`. The response lists the relative alarms read back off the saved reminder as `alarms_minutes_offsets` (minutes before). On the create and update tools, `alarms_note` appears in exactly four cases: (1) the stored relative alarms are not the ones asked for (`create_reminder`, each `create_reminders_batch` row, `update_reminder`; with `alarms_differ: true`); (2) a create skipped as a duplicate, which writes nothing (with `alarms_applied: false`); (3) an `update_reminder` without `alarms_minutes_offsets` that changes the due date (`due_date` or `clear_due_date`) when the saved reminder is date-only or has no due date and keeps relative alarms; this includes a timed `due_date` the store kept only as a day (no write change; the note gives the count, says the alarms never fire without a due date or that their firing on a date-only reminder is not measured, and gives `alarms_minutes_offsets: []` to remove them; after `clear_due_date` the count is read from the saved object without a re-read; a `due_date` whose re-read failed gets no such note, and `date_sync.aligned` is `false`); (4) the earliest time-based alarm on the saved reminder, relative or absolute, is not at its timed due date (#433), with the display note, on a create that passes `alarms_minutes_offsets` and on an `update_reminder` that passes `alarms_minutes_offsets`, `due_date` or `realign_to_due`, added after any other note. A call that touches none of them, such as a title change, gets no note, and neither does a date-only reminder, though #267 measured that the app goes on showing an absolute alarm's time there; so no note does not mean the list shows the due time. Measured list rows: `[15]`, `[60]`, `[2]`, `[15, 0]`, `[0]`, `[-15]`, absolute alarms at or before the due time, and `[15]` with an absolute alarm at the due time. Every other shape is inferred from them, for example `[60, 15]`, `[15, -15]`, `[-15, -60]`, `[1440]`, an absolute alarm after the due time, `[-15]` with an absolute alarm at the due time (no note), and `[15]` or `[0]` with an earlier one (note). They cannot decide `[0, -15]`: it gets no note for now, and release gate step 8 looks at it. The rows that showed the due time have no alarm before it, and an extra alarm at the due time did not bring it back (`[15]` with one read 15:15); firing was not checked on those 14 rows. Update-undo restores the previous alarms, the location alarm included (the snapshot already holds whole alarms). Tested in memory: that restore, and the #236 post-state guard comparing alarms by value (a reminder rebuilt with the same values passes, one whose alarm changed elsewhere is named `alarms`); what a synced store reads back is pending the release gate. A batch row that is refused fails alone.
- **Event read tools report the event's alarms** (#240, event-side counterpart of #231): `list_events`, `list_events_quick`, `search_events` and `check_conflicts` returned no alarm information, so a caller could not confirm what `alarms_minutes_offsets` wrote or see absolute-date alarms. Each event now carries `alarms` in the reminder shape: `{"kind": "relative", "minutes_before": n}` (measured from the start, positive = before, the sense of `alarms_minutes_offsets`) or `{"kind": "absolute", "absolute_date", "absolute_date_local"}`, absolute alarms first by date, then relative alarms earliest first, `[]` when none; a non-finite offset is left out. `absolute_date_local` is in the zone of the event's other `*_local` strings (`display_timezone` when given, otherwise the event's zone), where a reminder's is in the host zone as its other `*_local` strings are. Location alarms are not listed (events have no `location_trigger` field; the reminder output does not list them in `alarms` either). The key is emitted outside `detail_level: summary`, and `fields` accepts `alarms`. An occurrence reports the series' alarms unless it was edited on its own (then its own), as EventKit returns them. The reminder and event outputs are built by one helper (`AlarmReadOutput`), so the two cannot drift; the reminder output is unchanged. The four tool descriptions and their manifest summaries say so, and the `fields` descriptions of the three listing tools list `alarms`.
- **Event reads report each event's own time zone as `item_timezone`** (#386, event-side sister of #241): `list_events`, `search_events`, `list_events_quick` and `check_conflicts` report `timezone` as the event's zone, falling back to the host zone when the event stores none, so a floating event (all-day events included) looked the same as one stored in the host zone. The new `item_timezone` is the event's `EKEvent.timeZone`: a time zone identifier (usually IANA), or `null` when the event is floating. It is in every event dict, `detail_level: "summary"` included, and `fields` accepts it. `timezone` keeps its value, and `display_timezone` changes neither field (only the `*_local` strings). No existing key changes value or type; clients that reject unknown fields must update their decoders. The tool descriptions and the `detail_level` / `fields` lists say so.

- **All-day dates whose offset moves the day are reported** (#372, follow-up from #348): all-day dates are whole days read in this Mac's time zone (#364), and a `start_time` or `end_time` written with another offset is converted first, which can put it on another day (`end_time: 2027-04-11T23:59:59+07:00` on a `+08:00` host gives an event through 04-12). The event is still written that way (a refusal would break callers whose zone happens to agree); the response now carries a `warnings` list, present only when non-empty, whose entries give `field` (`start_time` / `end_time`), `written_day` (the first or last day in the offset the caller wrote), `host_day` (the day in this Mac's zone the request's dates are written with; nothing is written for a skipped duplicate) and a `message` with a value to send instead: for `start_time` the bare date; for `end_time` the last day at `T23:59:59` without an offset, or the bare date of the day after (a bare `written_day` as `end_time` would be an exclusive end and drop that day; PR #387 verify). It is added by `create_event` (also for a `skipped` duplicate, whose message then says the request's dates would be written that way and the existing event was not changed, since the existing event's own dates can differ; PR #387 verify round 3), by each `create_events_batch` result (created or skipped, worded the same way) and by `update_event` when the event is all-day after the call, only for the dates the call gave (the other end is the saved event's). The days are compared after the all-day rule, not the offsets: an offset that lands on the same day gives no warning, and an end at an exact midnight in the written offset (an exclusive end, last day 04-11) that is 01:00 in the host zone (an inclusive 04-12) does. A value without an offset never warns; the offset is the one the parser applied, read back from the parsed instant, so every suffix it accepts counts (`Z`, `±hh:mm`, `±hhmm`, `±hh`, `UTC`, `GMT+7`). The host offset on the event's date is used, so DST does not cause one. This is the first `warnings` field in the server. The tool descriptions of the three `start_time` / `end_time` pairs say so. `create_event` and `create_events_batch` (including its similar-events lookup) now reach EventKit through the same `EventWriteSource` seam as `update_event` (#268), so the warnings are tested through the handlers.
- **`list_reminders` and `search_reminders` report each reminder's own time zone as `item_timezone`** (#241): the per-reminder `timezone` was always the host zone, whatever zone the reminder stores, so a floating reminder (no stored zone, the kind iCloud Web shifts, #134 / #237) looked the same as one zoned in the host zone. The new `item_timezone` is the reminder's `EKCalendarItem.timeZone`: a time zone identifier (usually IANA), or `null` when the reminder stores no zone, which covers date-only and undated reminders too; a floating timed reminder is `item_timezone` null with `due.time` set. With a due date it matches `due.timezone`. Clients that reject unknown fields must update their decoders. `timezone` keeps its value and is now documented as what it always was: the host zone, the zone of the `*_local` strings. No existing key changes value or type. The tool descriptions say both.

### Changed

- **The Google results of the #261 probe are recorded** (#294): see the #261 entry under 1.20.0 and the `NewObjectSave` header. Exchange and local calendars were not measured.
- **The undo guard documents the moment it cannot see** (#424, docs only): the state a write left is read back right after the save, in the same synchronous stretch, so only another process can write in between; a change it makes then is recorded as the write's, and a later undo writes over it in the fields the undo writes back. Comparing with what was written was not chosen (it needs a measured list of the store's normalizations, and a missed one would refuse an undo for good); the limit is in `docs/UNDO_HISTORY.md`, the guard's doc comments and the `undo-history-discard` spec.
- **The event and calendar reads hand the server values, not EventKit objects** (#490, internal; responses unchanged except a calendar without a source, which now lists `""` and `Unknown` instead of trapping): `list_calendars`, `list_events`, `search_events`, `list_events_quick` and `check_conflicts` received `EKCalendar` / `EKEvent` objects from the `EventKitManager` actor and read their properties in the server's nonisolated handlers and in `formatEventDict`, off the actor that owns them (the remainder of #482). The manager now copies each event into an `EventReadValue` (every value `formatEventDict` reads) and each calendar into a `CalendarReadValue` on its actor, through `EventRangeReadSource` and a new `CalendarListSource`; `list_events_quick` and `check_conflicts` go through the range seam too. `list_events`, `search_events` and `list_events_quick` first read only start, end and all-day for every event, run their filter, sort and limit over those on the actor, and copy whole only the rows they keep: copying every event whole had cost about 4.5 s and 350 MB more at 182,605 occurrences, and picking first is within 0.1 s of the previous release and about 10 MB above it (`--cli`, a 100-year `list_events`, 2026-11-09). A calendar without a source now lists `""` and `Unknown` instead of trapping. No race had been observed. Tests compare the response formatted from the value with the one formatted from the live event, byte for byte, for all-day, recurring (end date, count, days), alarm, structured-location and time-zone events, and through a fake for attendees, the organizer and the other fragments; a probe actor whose events trap off it drives all five handlers; and a source pin keeps `Server.swift` free of `EKEvent` and `EKCalendar`.
- **The texts say what Google does to alarms after the save** (#317) — docs only: the `copy_event` and `undo` descriptions and both READMEs. Measured on a calendar hosted by Google: about a minute after the save an absolute alarm reads back as a relative alarm at the same time, and a location alarm that a copy or the undo of a one-off `delete_event` writes becomes a plain alarm at the start; relative alarms are kept. Google never listed an email alarm, though this Mac still reads it, and reading back shows only this Mac's view, so it cannot show whether Google lists the alarm. The response carries no note, because at save time the tool cannot see what the account will do. Not measured: Exchange, `delete_original`, `move_events_batch`, `create_events_batch`, and the undo of a series, an occurrence or a batch.
- **BREAKING (behavior) — a key a tool does not read, or a value of the wrong type, is refused** (#448): the MCP SDK does not validate arguments and the handlers read the keys they know, so both read as absent. A misspelled `timezone` on a `create_events_batch` row moved the event, a misspelled `due_date` on `create_reminder` made a reminder with no date, and a numeric `due_date` or a bare-string `tags` was dropped. Every tool now checks its arguments against its schema before the handler runs, and refuses with nothing done: an unknown key at the top level or in `structured_location` and `location_trigger`, and a value that is not the declared string, integer, number, array or object, the elements of an array of strings or integers included. The message lists the accepted keys and does not repeat the key given. A batch row with such a key or value fails alone, including `url` and `alarms_minutes_offsets` on a `create_events_batch` row, which were never read there. `recurrence` keeps its own messages and booleans their strict check. On a declared key the check treats JSON null as absent, though a handler may still refuse it (`limit`, for one); on an undeclared key it is refused like any other value. Text of the form `data:<type>,<content>` reaches the server as a data URL on the MCP path, and the refusal says so. **A call that sends an extra key works today and fails after this**, on all 29 tools. `update_event` reads `url` and now declares it. `list_calendars` also refuses a `type` other than `event` or `reminder`, which used to list every calendar, `Reminder` included.
- **Wide event reads are bounded** (#332): over a range longer than 1462 days, every read of events (`list_events`, `search_events`, `check_conflicts`, `find_duplicate_events`, and `delete_events_batch` by date range) stops with an error once it has passed about 200,000 event occurrences, returning nothing and deleting nothing. This is a safety valve, not an everyday limit: over 100 years it is about 2,000 occurrences a year (between five and six open-ended daily series, or about 40 weekly ones), and over the 400-year ceiling about 500 a year. All calendars read are counted together, on `search_events` before keywords are matched, and `limit` does not lift it. It is checked after each 1460-day part, which EventKit reads whole, so a read can pass it by that part's size. The error states the range and the way out for its tool: narrow the range or name one calendar; on `find_duplicate_events` narrow the range, or name fewer calendars but at least two; on `check_conflicts` a named calendar leaves the others unchecked; on `delete_events_batch` give both dates, at most 1460 days apart. Over such a range, without `limit` at most 500 events are returned, with `default_limit` (`metadata.default_limit` on `list_events`); a search given only `start_date` often has a range this long. On any range, `list_events` and `search_events` now report `truncated: true` when fewer events are returned than `event_count`, whether the default or a caller's `limit` (up to 10000) cut them; `event_count` is still the total. `list_events` keeps the first in its `sort`. `search_events`, which has no sort, now keeps the events closest to today on any cut, on any range and with or without `limit`, returns them sorted by start and says so in `truncation_note`: this changes which rows a `limit` returns on every range, since it used to take the first rows in read order, which is not date order and meant no particular set. The line moved from 1461 to 1462 days for the older wide-range limits too (2000 deletions, 2,000,000 comparisons), so that four calendar years across a clock change, 1461 days and an hour, count as narrow, and the default range of `search_events` and the `create_events_batch` hints is now two Gregorian years whatever calendar the host uses, which also stays under the line. `delete_calendar`'s `require_empty` is not bounded (each of its queries is narrower). Both numbers are defaults the maintainer may change. Measured on throwaway iCloud calendars with open-ended daily series (no user calendar was measured; host under load, wall times are upper bounds): reading 218,949 occurrences without the bound took about 4.1 s of CPU and 276 MB; a call stopped at the bound takes about 3.7 s of CPU and 257 MB; one series over 145,975 days took 17.4 s and answered 48.5 MB without a limit, of which the read was 1.7 s.
- **A created reminder or list whose save failed is no longer removed when its check cannot answer** (#289): when the save throws and a new store has no sources (so it cannot say whether the save committed), `create_reminder`, `create_reminders_batch` and `create_calendar` now keep the item instead of removing it from the store: a create has no undo record, so removing a save that did commit would delete it at the next write with nothing to bring it back. The call still fails, with a new error that names the save's code and says: the item was not removed and may already be saved; if not, it stays pending and the next save of any tool writes it, a retry's own save included (which would leave two); a check made right away proves nothing (through this server a pending item may be listed, and a pending reminder list reported as existing by `create_calendar`, without being saved; not tried), so do not create it again until another save or a restart has settled it; if it can never be written, later saves may fail until the server restarts, and a restart drops it (both not tried); this item has no undo entry, so undo removes the newest recorded operation (in a batch, possibly a later row), not this item. The undo of `delete_reminder` (single and batch) still removes the item, as before: its undo record is kept on failure, so a retry restores the reminder. The stderr line for both now names the save's error code. The branch was not produced on device; it is covered by unit tests.
- **`alarms_minutes_offsets` that is present but not an array is refused** (#333): `create_event` and `update_event` ignored such a value (a string, an object) and wrote the event without touching its alarms. The parameter is now read by one parser shared with the reminder tools, which refuses it (`alarms_minutes_offsets must be an array of integers`) before anything is written. Absent or JSON `null` is unchanged. - **`update_event` reads a date-only `occurrence_date` in the zone it searches in** (#383, sister of #270): the date was read in the request's `timezone` (the zone the event gets after the update), or in this Mac's zone without one, while the occurrence was searched in `timezone`, or the event's zone without one. When those zones put that midnight on different days, the search landed on the neighbouring day: "no occurrence", or the neighbouring occurrence updated. Example: host Asia/Taipei, a daily series at 23:30 America/New_York, `occurrence_date: "2026-12-06"` was read as Dec 6 00:00 Taipei, the Dec 5 New York occurrence. A value without an offset is now read, and searched, in the event's current zone, as `delete_event` and `move_events_batch` do since #270 (calendar access ensured and the event refreshed first; a floating or all-day series reads the value in this Mac's zone and searches in it). A value with an offset is used as given; span `all` does not look up the zone. The lookup runs after every parameter check that needs no calendar, so a malformed call is refused without touching EventKit. **Behaviour change**, for calls that pass `timezone`: an offset-less `occurrence_date` used to be read in the new `timezone`, and the day of any `occurrence_date` (with or without an offset) used to be taken in `timezone`; both now use the zone the event has before the update, the one the occurrence sits in. The `occurrence_date` description says so. When `occurrence_date` picked one occurrence (span `this` or `future`), the response adds `occurrence_start`: that occurrence's start before the update, ISO 8601 with the offset of the event's zone (this Mac's for a floating series), so a caller can see which day was edited.

- **A reminder saved into a list deleted elsewhere is no longer reported as created** (#281): when the list is deleted by another app or device after `create_reminder` has looked it up and before it saves, EventKit returns from the save without an error and writes nothing (checked on device, iCloud). The tool used to return an identifier and record an undo entry for a reminder that does not exist. After a save that returns, the server now asks its store (as it is, without a refresh) whether the list and the reminder still resolve; when the list reads gone and the reminder does not resolve (the pair a save into a deleted list leaves; either one alone counts as written, so a transient read cannot turn a real save into a failure), the call fails with "The reminder list was deleted while the reminder was being saved; nothing was created." and records no undo entry. `create_reminders_batch` reports that error on the item. The undo of `delete_reminder`, which recreates the reminder the same way, fails with its own message and keeps its history entry; the next undo reports the list as unavailable and says how to give the entry up. Through the server the window is narrow: a list deleted before a call is already reported as not found by that call, so only a deletion that lands inside one call reaches this check. **Boundary**: the check sees only what the server's store has seen; a deletion it has not yet seen when it checks is not caught, and that save is still reported as created (the original symptom, now only in that window). On device the store had always seen the deletion (saves 15 to 17 ms after it), and how late a deletion can become visible was not measured. After such a save, the same store's next reminder and event saves commit normally and the unwritten reminder never appears (checked on device). Not changed: a new reminder list saved into an account deleted elsewhere (not probed). Other sources than iCloud were not checked.
- **The redo refusal of a one-member mixed batch says "1 operation"** (#296): `Cannot redo this batch of 1 operations` is now singular, as the other batch texts already were (PR #282).
- **A failed save in the undo of `update_event` or of an in-place move is rolled back** (#274): the update-undo arm wrote the old values onto the cached event and the move-undo arm assigned the original calendar, then saved; when that save threw (a read-only or deleted calendar, a sync conflict), the restored values stayed on the event in memory. Both arms now call `rollback()` on the event before returning the error, as `updateEvent` does since #379 and the in-place move did already. `executeRedo` writes no event (#247), so it needed no change. This is pinned in the source only (`EventUndoRollbackTests`); what EventKit keeps after a failed save of an existing event was checked on a device by #261 (the store drops it, the failed instance keeps it), not again here. #274 then measured that a failed save of an event leaves nothing pending, with or without this `rollback()`, which only clears `hasChanges`; the reminder saves are in the #274 entry above.
- **Live `ps` and `sqlite3` tests no longer fail on the 500 ms production budget of a loaded host** (#315, tests only): `LiveProcessInventorySourceTests` (empty-match test) and `LiveTCCDatabaseSourceTests` (corrupt and synthetic database tests) read what the real tool printed under the production 500 ms timeout, so a busy host failed them with "timed out" (captured 2026-11-05 at load average about 830). - **`update_event` and `update_reminder` report the identifier the item has after the save** (#268): both answered with the identifier the call passed. A `calendar_name` (and `calendar_source`) naming a calendar in another account reassigns the event in place, which gives it a new identifier (#226, device: iCloud → Google), so the response named an id that no longer resolved. The response's `id` is now the saved event's `eventIdentifier` (the reminder's `calendarItemIdentifier`), with `id_changed` (as `move_events_batch` and `copy_event` report it) and, only when it changed, `previous_id` with the identifier passed in. `id` changes (`id_changed: true`) in exactly three cases: (1) `calendar_name` moves the item to a calendar or list in another account (an `update_event` that edits one occurrence, `occurrence_date` with span `this`, and names a calendar of another account is refused before anything is written, since a new calendar moves the whole series and the new series' identifier could not be read back reliably from an occurrence save or checked on a device; a calendar whose account cannot be read counts as another account, as for the stand-in refusal; PR #387 verify round 4); (2) `update_event` with `span: "future"` from a later occurrence, which EventKit performs by ending the series and starting a new one, answers with the new series' identifier (checked on iCloud, 2026-11-04: the returned id is the one the later occurrences list under); (3) `update_event` with span `all` or `future` and the identifier of an occurrence edited on its own that is the first occurrence left after the first was deleted gives what remains a new identifier (#416, device, iCloud; span `future` from a later edited occurrence is case 2, and span `all` with an earlier occurrence left is refused). In every other case `id` is the input and `id_changed` is `false`. An edit of one occurrence (`occurrence_date` with span `this`) saves a detached occurrence, which on iCloud reads back as the series id followed by `/RID=` and a number (device, 2026-11-04; that id addresses only the occurrence, and the series id still needs `occurrence_date`). Which saves are occurrence saves is taken from the save itself (the saved object is an occurrence, not the resolved series), not from the id's shape, so other stores' occurrence ids are covered too; the response answers the series' identifier after the save as `id` and adds `occurrence_id` with the occurrence's own identifier (what each span does through it: #416). The series object's identifier is used only when it refreshed after the save and is a real series object (not the stand-in of a series whose first occurrence was deleted, #326), with any `/RID=` part stripped; otherwise the part of the occurrence id before `/RID=`, else the input (PR #387 verify rounds 3-4). Within one iCloud account a calendar change of an event and a list change of a reminder kept their identifiers (`id_changed: false`, device). Cross-account moves were not checked on a device for this change: the event case follows #226's finding, and whether a reminder moved to another account's list gets a new identifier is unknown. `update_event` now reaches EventKit through a narrow `EventWriteSource` seam so the handler is tested with a fake.
- **The undo error for a missing reminder list no longer names the list or its account** (#290): when a reminder's list is gone (deleted, or its account turned off or still syncing), the undo of `update_reminder` / `delete_reminder` is refused with a message (#242) that named the list's title and the account's name next to the instruction to give the undo up with `discard_id`. A shared list's title is set by someone else and an account name is often an e-mail address, so neither belongs in that trusted text (#37); the batch pre-check's refusal already names neither (#248). This replaces the wording described in the #242 entry below ("names the list, its account and the reminder") and the #248 entry's note that the missing-list error names the list and account.
- **Recording the undo of an event without a calendar no longer crashes the server** (#286): `EventSnapshot` read the event's calendar through EventKit's implicitly unwrapped `calendar`, so building the undo record of an event whose calendar is nil trapped the process and the undo history was lost. The reminder side has been safe since #242 (PR #277). Whether EventKit ever returns a fetched event without a calendar is not known; the change is defensive.

The all-day + `timezone` conflict (#190) ran after the title, dates, all-day flag, notes and location were assigned; the weekday check of a weekly rule (#5) ran after those and the URL, time zone, calendar and alarms too. Every check that can refuse now runs before the first field is assigned, reading the values the event will have after the update. Every other accepted call gives the same result as before.
- **`make install` and `make install-signed` install a product they built and checked in the same run** (#239): they copied `.build/release/CheICalMCP`, which under the swiftbuild build system is a directory every `--arch` build writes to (after `scripts/build-mcpb.sh` it holds the x86_64-only product). The start-only call now keeps the number of days the timed range touched (two for `22:00` to `02:00`, one for `22:00` to `00:00`), the same count the flag-only call gives, read in this Mac's time zone. Moving back to a calendar of another account through the stand-in is refused, as the move itself is; the entry is kept. ### Changed

- **The self-disclaim rule depends on the host's grant, and is the same for every host** (#343, verify round 2): v1.22.0 re-exec'd by default only when Claude Code was the responsible process. ## [1.20.0] - 2026-10-10

### Added

- **`list_reminders` and `search_reminders` report the start date and time-based alarms** (#231). Reminders.app shows both, and a reminder with only a start date or only an alarm used to look undated through these tools (the #227 situation). New fields: `start` (the start date in the `due` shape, `null` when absent; a start that EventKit fills in can carry `nanosecond = 0` and then shows `.000` milliseconds, `10:00:00.000`, where an otherwise equal `due` shows `10:00:00`, [#252](https://github.com/PsychQuant/che-ical-mcp/issues/252)), `start_date` / `start_date_local` (mirroring `due_date` / `due_date_local`, present only when set), and `alarms`, always present (`[]` when none): `{"kind": "relative", "minutes_before": N}` (positive = before the due date, negative = after) or `{"kind": "absolute", "absolute_date", "absolute_date_local"}`. Absolute alarms are listed first by date, then relative alarms earliest first, because EventKit's own alarm order changes between processes; a relative offset that is not a finite number is left out. Location alarms are not listed in `alarms`; they stay in `location_trigger`, which, as before, reports only the first location alarm EventKit returns. Additive only: clients that reject unknown fields must update their decoders. Event alarms are not covered (#240).
- **`update_reminder` `realign_to_due` repairs a reminder whose alarm disagrees with its due date** (#235): `due_date` moves the start date and absolute-date alarms by the change in the due date (#227), which keeps any offset that already exists. A reminder left diverged by v1.17/v1.18 (due moved, alarm stayed), one that had no due date before, or a date-only due given a time on the same day therefore kept showing the alarm's date in Reminders.app, and nothing in the tool could move it. The new strict-boolean `realign_to_due` puts them onto the due date instead, whatever it moved by: together with `due_date` onto the new due date, on its own onto the current one. The anchor is the earliest absolute-date alarm, because that is the date Reminders.app displays (checked on device: with several alarms the app shows the earliest, before or after the due date). With a timed due every absolute-date alarm moves by the difference between the due and that alarm, so it lands on the due and later alarms keep their spacing after it; with several alarms, a stale alarm earlier than an intended early alarm therefore pushes the early one past the due. With a date-only due they move by whole calendar days onto the due's day and keep their time of day. An existing start date is set to the due date unless it already agrees with it by the rule `aligned` uses (below), in which case it is left as it is, so realigning an aligned reminder changes nothing. A timed due written back by `realign_to_due` alone gets a zone on a floating reminder, as with `due_date` (#237). Relative and location alarms are unchanged, and undo restores the previous dates. `realign_to_due` is refused together with `clear_due_date`, and refused before anything is written when the reminder has no due date and none is given. Without `realign_to_due`, the start date and alarms still move by the change in the due date (#227).
- **`date_sync.aligned`** (#235): `update_reminder`'s `date_sync` reports whether the start date and the earliest absolute-date alarm agree with the due date, judged on the reminder as read back after the save. The start agrees when, for a date-only due, it is on the due's day at any time, and when, for a timed due, it is at the due instant or on the due's day at midnight or without a time (the store hands date-only starts back as `00:00`). The earliest alarm agrees at the due instant, or on the due's day for a date-only due. A timed due that could only be saved without its time or without its zone reads `false`, and so does a reminder that could not be read back after the save. It is omitted when the update leaves no due date, and `date_sync` is now also returned for a call that passes only `realign_to_due`. An alarm set apart from the due date on purpose also reads `false`: the field reports, it does not decide. It sees what EventKit returns: store rows EventKit hides, like the duplicate alarm rows under *Changed*, stay invisible to it.

A day the host zone skipped (Pacific/Apia has no 2011-12-30) has no midnight: it prints, sorts and turns overdue at the next instant that exists, 00:00 the next day.
- **BREAKING (behavior) — a bare-date `due_date` makes a date-only reminder** (#267): `create_reminder`, `create_reminders_batch` and `update_reminder` stored a `due_date` given as `YYYY-MM-DD` as 00:00 of that day with a time, so Reminders.app showed it at 12:00 AM and treated it as overdue from midnight, and nothing in the tool could write a reminder with a date and no time, as the app itself makes one. A bare `YYYY-MM-DD` now writes the day without a time, and the start date as the same day, as Reminders.app does; read back, `due.time` is `null`. Any other form (with a time, with or without an offset) is parsed as before, and a bare date that is not a day (`2026-02-30`) is refused as before. On `update_reminder` a date-only due also sets the start date to that day and removes every absolute-date alarm, because Reminders.app displays the earliest absolute-date alarm: on device (iCloud, 2026-10-09) a timed reminder turned date-only with its alarm kept was stored all-day but the app went on showing the alarm's old date and time. Relative and location alarms are kept; `date_sync` reports the start (`shifted`, `set` or `unchanged`) and counts the removed alarms in `absolute_alarms_removed`; when any were removed, the response's `note` says how many and that undo restores them while the server is running, if the reminder has not been changed since (the undo history does not survive a restart, a change made after the update makes undo refuse, #236, and undo through the tool was not run on device, nor was the recreation of a date-only reminder by delete-undo, now a pre-release check in #264; redo of an update writes nothing since #247), and `realign_to_due` adds nothing to a bare date. Giving a timed reminder its own date removes its time. The written day carries no time zone: EventKit dropped one given to date-only components as they were written, and the stored reminder was floating and marked all-day in the Reminders store. Undo of such an update writes the recorded timed due, start and alarm back; the write order it uses brought them back on device, while undo through the tool itself was not run on device. The `create_reminder` duplicate check keeps its rule: a bare date compares as 00:00 of that day, so a retry after upgrading still finds a reminder an earlier version stored at 00:00 from the same bare date instead of making a second, date-only copy. Such a `skipped` answer carries a `note` saying the existing reminder has a time and that `update_reminder` with the bare date makes it date-only; the comparison now reads dates in the Gregorian calendar EventKit uses, not in the calendar chosen in region settings, and reads a stored date-only due as 00:00 in the host zone whatever zone it carries, so on a Buddhist, ROC or other non-Gregorian host calendar, or for a stored date-only due with a zone of its own (the iCloud lists checked hand them back without one), its result can differ from before (since #299 the timed write and read paths use the Gregorian calendar too). Checked on iCloud only.
- **`update_reminder` re-reads the reminder before and after writing, and a `due_date` update can save twice** (#235, #237): the reminder is re-read before the update, both where the write starts and where `notes` and tags are merged, so edits made in Reminders.app since the server cached it are the base of the write and of the undo record; one that can no longer be read is reported as not found. Every check that can refuse the call, including the `calendar_name` lookup, runs before anything is written, and a failed save is rolled back. When the update touches the due date (`due_date`, `realign_to_due`), the reminder is read back after the save; other updates are saved once and not read back. If a timed due came back without its time or zone, the #237 fallback is written and the reminder saved a second time; stderr gets a line with constant text when that happens, and a failed second save is rolled back and logged with its sanitized code (`eventkit_error_<N>` for an EventKit error; otherwise the generic `error_<domain>_<N>`, or `error_unknown` for a Swift error), never with the reminder's content. If the reminder cannot be read back, `aligned` is `false`. Known limit: a reminder source that never hands the due date's zone back would save twice on every timed due update and never report `aligned: true`; the iCloud and Exchange lists checked on device keep the zone and saved once.
- **Moved alarms are written as new alarms** (#235), on the #227 path as well as with `realign_to_due`: a moved alarm used to be a copy of the old one. On device, a copy kept the old alarm's identifier, and when the start date was written without a due-date change the Reminders store kept both rows, so the app went on showing the old date while EventKit read back only the new one. A moved alarm keeps only its sound and email, the other settings an absolute-date alarm has (the procedure URL has been deprecated since macOS 10.9).
- **BREAKING (behavior) — `undo` / `redo` refuse to overwrite a change a person made after the operation** (#236): undo looked the item up by its recorded identifier and wrote unconditionally, so an event edited or moved elsewhere after `update_event` / `move_events_batch` was silently reverted, and an event or reminder edited after it was created was deleted with the edit. Each create, update, move and completion record now also keeps the state its write left, and undo first re-reads the item from the store and compares. A field blocks the undo only when it changed since the write **and** the undo would change it again: a title changed back by hand is already at the value the undo writes and does not block it. What is compared: for an update of a one-off event, the fields the undo writes back (an update that touched a recurring event is not undone at all, see the next entry); for a create, whose undo deletes the item, every recorded field (the calendar or list and the alarms included), and for a recurring event also whether any occurrence was edited on its own (an occurrence counts when it was moved off the start its rule gives it, or differs from the series in any compared field: title, notes, location, URL, all-day flag, duration, alarms, time zone, place or availability (availability since #245, compared only when both the occurrence and the series report one), with the same two exemptions as below; one back at the series' values does not, though it stays detached); for a move, the calendar; for a completion, the completion state and time. Two changes a calendar app or server makes on its own are not treated as edits: an alarm sound, and coordinates added to a place recorded without them; they never block an undo, and an update-undo overwrites them with the recorded values. A different time-zone spelling of the same due time, the order of recurrence days and sub-second differences are not changes either. On a refusal nothing is written, the error names the changed fields, and the entry stays on top of `undo_history`: whoever made the change decides whether to change it back and undo again, or to give up that undo with `undo` + `discard_id`. Three create-undo refusals offer only the second: occurrences of the series edited on their own (`modified_occurrences`), which cannot be put back into the series; a series whose occurrences could not be checked because it has no identifier or calendar (`unchecked_occurrences`); and a series whose rule was shortened (`recurrence`: the same rule with a smaller count, an earlier end, or an end where there was none; an update or delete of an occurrence and the following ones does this), whose cut-off part cannot be put back; any other change of the rule can be changed back. A completion of a recurring reminder recorded without an occurrence snapshot (#204) is undone or redone only while the reminder is exactly as expected. When its identifier resolves to a reminder that still repeats with the opposite completion (what a rollover leaves), nothing is written and the entry is discarded, as #204 does, so earlier operations stay undoable; any other mismatch is refused and the entry kept. A redo after the reminder was completed elsewhere following the undo is not caught: the next occurrence looks exactly like the state the undo left. Redo of a completion makes the same check against the state the undo left. Not covered: properties the snapshots do not record (attendees, reminder subtasks); undo of any update that touched a recurring event, which is refused (a safe restore is designed in #263); a series shortened by an update or delete of an occurrence and the following ones, whose create-undo can only be given up (a new series split off by an update is left to be deleted by hand); a series move-undo, which writes the whole series by design (#226); for the occurrence check, an edited occurrence moved outside the series' dates and anything more than four years after the first occurrence (which includes the later part of a long count-based series); and stores other than iCloud, which were not checked on device. Delete-undo (which recreates) is otherwise unchanged by this entry (#244 and #245 below change it), but `delete_event`, `delete_events_batch`, `delete_reminder`, `delete_reminders_batch`, `copy_event` and `move_events_batch` now refresh the item before they record it, so an edit made elsewhere is not lost from what delete-undo recreates; an item whose refresh fails is reported as not found.
- **BREAKING (behavior) — undo of an `update_event` that touched a recurring event is refused** (#236, #262): an update of one occurrence (`occurrence_date`, span "this", or a detached occurrence addressed by its own identifier), of an occurrence and the following ones (span "future"), of the whole series (span "all"), or one that made a one-off event repeat or removed a series' repetition (`clear_recurrence`), is recorded in `undo_history` only as `Updated recurring event: <title> (undo not available)`. `undo` on it writes nothing and fails with a message that names the kind of change and says to revert it in Calendar (or with `update_event`) if it should be reverted; the entry is discarded, so earlier operations stay undoable. The undo of an update or a move recorded on a one-off event is refused the same way when the event repeats or is an edited occurrence by the time of the undo (a later update made it repeat, or another app did; a move of an item that was already an edited occurrence is refused too), so update-undo and the undo of a one-off move never write to a recurring event; a series move-undo writes the whole series back by design (#226). The restores this removes, all of which existed in v1.19.0: an occurrence update (it wrote the series' values onto the occurrence's slot or onto the first occurrence), a span "future" update (it restored only the occurrence onto the new series), a span "all" update (it deleted the rest of the series, #262), rules added (it could not remove them) and `clear_recurrence` (it wrote the rules back with `.thisEvent`). Undo of an update to a one-off event is unchanged. A safe restore for recurring updates is the follow-up #263 (https://github.com/PsychQuant/che-ical-mcp/issues/263).
- **BREAKING (behavior) — `redo` of a record it cannot redo writes nothing, leaves the undo history alone and answers `success: false`** (#247): only completions are written again on redo. For a create, delete, update or move, `redo` returned an instruction and wrote nothing, yet moved the record back onto the undo stack and answered `success: true`; the next `undo` then undid the same operation again. After a delete that recreated the event or reminder a second time (a batch delete: every member again, after a redo that answered "Redone batch (N operations)"); after a create it blocked older history; after an update or move it rewrote the same values, or silently reverted a change the user had re-applied by hand. Now the undo stack is unchanged and `redo` answers `{"action": "redo", "success": false, "message": …, "undo_available": …, "redo_available": …}`; the message names the title and the tool that repeats the operation (`delete_event`, `delete_events_batch`, `update_reminder`, …) and no longer the item's identifier, which an update-undo across accounts changes (#246). The instruction is returned once and the entry is then dropped from redo history, and the next `redo` applies to whatever is then on top of the redo history (an older undone operation, which may itself be one that redo only answers) instead of answering the same instruction until a new change clears the redo history; the message says so, and `redo_available` counts the entries left. Redo of a completion is unchanged. "Nothing to redo" now carries the same `undo_available` / `redo_available` counts.

### Fixed

- **Undo of a created series refuses when one occurrence was moved in time** (#311): the scan for occurrences edited on their own read each occurrence's original start from `occurrenceDate`, and in a long-lived server that value equalled the occurrence's new start, so a moved occurrence passed as unedited and the create-undo deleted the whole series. The original start now comes from the `RID` in the occurrence's identifier (seconds since 2001-01-01 UTC, read off an iCloud device on 2026-10-10), and from `occurrenceDate` only when there is none. Checked on device with a move of 30 minutes and of one day made in another process, and a move made by `update_event` itself; each is refused and the series stays whole.
- **Reminder dates and date inputs are read and written in the Gregorian calendar, not the one chosen in region settings** (#299): the reminder code turned dates into components and back with the host calendar (`Calendar.current`, and date formatters whose calendar came from the host locale), while EventKit's components are Gregorian. On a Mac whose region calendar is Buddhist, ROC, Japanese or Islamic, a timed `due_date` given to `create_reminder`, `create_reminders_batch` or `update_reminder` was stored in the wrong year (2569 for 2026 under the Buddhist calendar), `update_reminder` then moved the start date and alarms by about 543 years, `list_reminders` / `search_reminders` read every stored due and start in the wrong year (`due_date`, `start_date`, `is_overdue`, `filter: "overdue"`, `sort: "due_date"`), and a retried timed `create_reminder` did not find its own duplicate. The timed due of both writers is now built by one function, Gregorian, with the host zone attached (#134) and no calendar attached; stored components are read in the calendar they carry, else Gregorian. **Event inputs are fixed as well**: the date parser is shared, so a date-time without an offset (`2026-02-06T14:00:00`), a bare date and a time of day given to any tool are now read as Gregorian with a POSIX locale on such a host too. On a Gregorian host nothing changes, with one exception in the `create_reminder` duplicate check: a bare date now compares with a stored date-only due by year, month and day, and with a timed due through the day's 00:00 in the host zone only when the zone has that midnight. In a zone that skipped a day (Pacific/Apia skipped 2011-12-30), a bare date for the skipped day no longer counts as a duplicate of a reminder due the next day. Checked with Foundation and source pins only, and with the unit tests run under a Buddhist launch locale; not on a device whose region calendar is not Gregorian. The `*_local` strings are still formatted in the host calendar (#304).
- **Undo of a delete of one occurrence no longer recreates the whole series beside the surviving one** (#244): `delete_event` with `occurrence_date`, and `delete_events_batch` by calendar and date range over occurrences of a series, recorded the whole series whatever the delete removed, and undo recreated it as a new series next to the original (on device: a weekly series of 3, delete the 2nd, undo, 5 events). A delete record now says what the delete removed. Span "this": undo restores the occurrence as a one-off event at its start and end, since EventKit has no public way to put an occurrence back into its series; `undo_history` lists it as `Deleted occurrence of event: <title> (undo restores it as a one-off event)`. An absolute-date alarm of the series becomes an alarm at the occurrence's start, as when a move splits an occurrence out, and the undo text names it (`absolute_alarms`), once for a batch. The last occurrence left comes back as a one-off as well (listed as `Deleted event` when EventKit has already dropped the series' rules from it; on device, 2026-10-08: after a batch removed the 2nd and 3rd of three, the 1st had no rules, and its delete was listed as `Deleted event` and came back as a one-off). A batch by date range with span "this" over every occurrence of a series does not get past the first one on iCloud: once that occurrence is deleted, the series reads as not found, so the later occurrences fail with `Event not found` and stay (#284); undo restores the first occurrence as a one-off (on device, 2026-10-08). With span "future" the first item removes the whole series, the later items are reported as failed (#279), and undo recreates the series from its rules (on device, 2026-10-07). Span "future" from the series' first occurrence, which removes all of it, and `span: "all"`: undo recreates the series from its rules, as before (on device, 2026-10-08: a timed, an all-day and a New York series each came back with its 3 occurrences after span "future"). The rules are all it restores: an occurrence deleted on its own earlier comes back, an occurrence edited on its own comes back without its edit, and undoing the earlier delete of that occurrence as well then leaves it twice (#285; on device, 2026-10-08: the deleted occurrence came back with span "future" and with `span: "all"`; the edit lost and the occurrence left twice were seen with span "future" only, and follow for `span: "all"` from the same snapshot, not run). The undo text says so (`Restored from the series rules: …`), once for a batch, for every series restored from its rules, whether or not any of its occurrences was deleted or edited on its own; `undo_history` lists such a record as `Deleted event: <title> (undo recreates the series from its rules: occurrences deleted on their own earlier come back, edited ones without their edits)`, and a `delete_events_batch` record that removed a series whole (a batch is recorded even for one event) as `Batch (<N> operations; undo recreates <K> series from its rules: …)` (`their rules` for more than one, `1 operation` for one); a batch that also holds a span "future" delete undo refuses, at any depth, is listed as `Batch (<N> operations; undo not available: a member deleted an occurrence and the following ones of a recurring event)` instead, since its undo writes nothing. The second copy is written by the later undo of the earlier single-occurrence delete, whose own text does not warn of it; the warning is in the series' undo text, one response before. iCloud removed the edited occurrences with the series; a store that kept them would get the series back beside them (not checked). The series is recorded whole when the delete started at the series' first occurrence and a lookup afterwards no longer finds the series' identifier. The start at the first occurrence is the only evidence: the lookup cannot tell a series that is gone from one it failed to find, so a lookup that finds nothing counts as gone. It is asked only after a delete from the first occurrence, which removes the whole series. Every other span "future" delete is refused: one that left part of the series, one that started at the last occurrence (it removes only that one, but nothing tells it apart), one that started at the first occurrence left after the series' first ones were deleted (iCloud keeps the series' original start, and recreating the series would bring the deleted ones back; today such a delete fails before it starts, #284), and one that named a detached occurrence by its own identifier, which also removes the following occurrences of its series (checked on iCloud) and whose undo used to restore that occurrence alone. Such an undo writes nothing, says to restore the occurrences in Calendar, and discards the entry, so earlier operations stay undoable; it is listed as `Deleted occurrences of recurring event: <title> (undo not available)`. The issue asked to keep that entry; the maintainer chose to discard it, as for the refused undo of a recurring update (#236, #262), because a kept entry would refuse on every undo and hold the older ones back until `discard_id`. A `delete_events_batch` that holds such a delete is refused before any of its events is restored, and discarded; that is all the check promises (a batch undo that fails part way through is #248). Deletes of one-off events are unchanged; `span: "all"` is recorded as before and has the rules-only limit above. Checked on iCloud only; other stores were not checked on device.
- **Delete-undo keeps an event's availability** (#245): the undo snapshot did not record availability, so every delete-undo (`delete_event`, `delete_events_batch`, `span: "all"`, and the original restored after a split or fallback-copy move) recreated the event with the calendar's default, busy on iCloud: a free, tentative or unavailable event came back busy. The snapshot now records it, and undo writes it back after the calendar is set, only when that calendar supports the value; otherwise the calendar default stays and the restore still succeeds. The post-state guard (#236) compares it like the other recorded fields: an availability changed elsewhere after a create or an update blocks that undo (an update-undo not when it is already back at the recorded value), and an occurrence of a created series with an availability of its own counts as edited (`modified_occurrences`), when both the occurrence and the series report one (on iCloud both do, checked on device: an untouched series' create-undo goes ahead, one occurrence made free refuses it). That exemption leans one way: on a store that reports availability on one side only, an occurrence's own availability is not seen as an edit, and the create-undo deletes it with the series. The series and one-off events are compared strictly, so there a value reported on one read and not on the other blocks the undo. Both follow from the comparison and are unit-tested; neither was seen on device, where iCloud reports a value on both sides. Copies (`copy_event`, the copy of a split or fallback move) still do not carry it (#272).
- **`date_sync.start_date` describes the saved reminder** (#235): on a reminder without a due date, writing one makes EventKit create a start date equal to it, and the response reported `absent`. The start date is now compared before and after the write, so that case reads `set` (a new value); a date-only start that only gains a time or a zone without moving reads `unchanged`.
- **`update_reminder` keeps the explicit time zone on a due date written to a floating reminder** (#237, a gap in #134): a reminder has one time zone shared by its start and due dates, and when that zone is floating (reminders made date-only in Reminders.app or written without a zone by another client) EventKit stored the new due date floating, so iCloud Web could still show it shifted by the UTC offset. After writing a timed due date the reminder is now given the due date's zone; start and due keep their wall clock. A reminder that already has a zone is left alone, because changing it would move its dates. If the due date read back after the save still lacks its time or zone, the start date is cleared, the due date written, the start put back with the same wall clock in the due date's zone, and the reminder saved again.
- **Undo of `update_reminder` / `delete_reminder` keeps location alarms, recurrence and the URL** (#228): the undo snapshot kept each alarm as a relative offset (or, since #227, an absolute date), so a location alarm (offset 0, no date) came back as an alarm at the due time. That happened on every update-undo, whatever the update changed, and undoing `clear_location_trigger` added a due-time alarm instead of the location alarm. Delete-undo also recreated a repeating reminder as a one-off and dropped its URL. The snapshot now keeps each alarm's time, absolute date and location (with radius and proximity), the recurrence rules and the URL. The rules include the week start, which decides where an every-other-week rule falls; EventKit has no public setter for it, so it is written back through the run-time one (checked on an iCloud list and calendar: saved and read back). Only the alarms that differ are rewritten, and the rules only when they differ, so an undo that did not touch them leaves them as they are. Reminder alarm sounds and email addresses are not stored by iCloud, so there is nothing to restore for them.
- **Undo of `update_reminder` / `delete_reminder` restores into the list the reminder was in** (#242): the list was looked up by its title, so with two lists of the same name in different accounts (iCloud and Exchange both have a "Reminders" list by default) the reminder went to whichever came first. After the list was renamed, undoing an update that had moved the reminder to another list left it there without saying so, and a delete-undo failed with EventKit's own error. The list is now looked up by its recorded identifier, as event undo looks up the calendar (#208): a renamed list is found, and a list of the same name in another account is never used instead. Before the lists are read, Reminders access is checked and, if this server has written since its last refresh, the store's sources are refreshed; a list that another client or an account sync added since then may not be seen yet, which is what the message's advice to run undo again covers. When the list is not found (deleted, or its account turned off or not synced yet), undo writes nothing for that reminder, keeps the entry, and fails with a message that names the list, its account and the reminder and says how to give the undo up with `discard_id`. It also says that giving up cannot be reversed: after a `delete_reminder`, the deleted reminder can then no longer be recreated through undo, and after an `update_reminder` it stays as it is. Older undo entries stay blocked until the entry is undone or given up. One case that used to report success is now refused this way: the undo of an `update_reminder` that moved the reminder out of a list deleted since then, which left the reminder where it was. The event side's message for a missing calendar still names only its identifier (#269).
- **Undo of `update_reminder` / `delete_reminder` writes the start date before the due date** (#251): it wrote the recorded due date first, and EventKit turns a timed due date-only when a date-only start is written after it (seen in memory), so the due could come back without its time. The dates are now written in the order `update_reminder` writes them: the start first, then the due, a zoned due the way `due_date` writes one (#237); a start that was recorded as absent is cleared afterwards, because EventKit creates one when a due is written. Beside a zoned due, a recorded date-only start comes back as 00:00 of its day in the due's zone: writing a date-only start leaves the reminder floating, and writing the due that way gives a floating reminder's date-only start that time. This was seen in memory; what the store keeps after the save was not checked. A date-only or absent due is written as before. This is a defensive fix: the store hands a date-only start back as `00:00`, so a reminder read from the store probably never holds this combination, and no case from a stored reminder is known. Not changed: the reminder's own time zone is not recorded, so delete-undo can still recreate a zoned reminder as floating (#275).
- **Undo of `update_event` / `delete_event` keeps absolute-date, location and email alarms** (#230): the snapshot kept one relative offset per alarm, so undo turned absolute-date and location alarms into alarms at the event start and email alarms into display alarms, even after an update that did not touch the alarms. The snapshot now keeps each alarm's time, absolute date, location, email address and sound, and only the alarms that differ are rewritten. The exception is a procedure alarm (one that opens a file or runs a script): the file is not recorded, so such an alarm stays as it is while it is unchanged, but one that has to be recreated (delete-undo) comes back as a display alarm at the same time.
- **`copy_event` keeps absolute-date, location and email alarms and alarm sounds** (#230): the copy (also the copy of `move_events_batch` when it falls back to copy + delete) rebuilt every alarm from its offset, while the tool description said absolute-date alarms were not copied. Alarms are now copied with their date, location, email address and sound; a procedure alarm becomes a display alarm at the same time. A fallback copy no longer lists `absolute_alarms` in `not_carried_over`. An occurrence split out of a series (`move_events_batch` with `span: this`) is the exception: the series' absolute date would lie before a later occurrence, so, as before, such an alarm becomes an alarm at the occurrence start and `not_carried_over` lists `absolute_alarms`. Whether a calendar outside iCloud accepts location, email and sound alarms is not verified, so a copy that used to succeed with those alarms turned into plain alarms can now fail. If saving a copy that carries them fails, for whatever reason, the error gives the underlying error code and names those alarm kinds (`location_alarms`, `email_alarms`, `alarm_sounds`) as a possible cause. The copy is saved before an original is removed, so a failed move does not remove the original.
- The 1.19.0 note "undo still restores alarms by date only, #228" is superseded by the two undo entries above.
- **Undo of a `span: "all"` `update_event` no longer deletes the series** (#262): it saved the restored first occurrence alone, so on iCloud the first occurrence became a detached copy with the old values and every other occurrence of the series was removed (data loss, in v1.19.0 and earlier). That undo is now refused and writes nothing (see the BREAKING entry above).
- **Titles in `undo_history` and in undo / redo texts drop invisible characters** (#236): the descriptions, the "Undone: …" / "Redone: …" texts and the redo instructions remove control and format characters and other default-ignorable code points (bidirectional controls, zero-width characters, tags…) from the title, keeping ZWJ, ZWNJ and visible format marks; quotes and length are unchanged. Undo errors show the title the same way, with its quotes replaced and at most 120 characters.
- **Undo of `create_reminder` on a reminder that no longer exists reports not found** (#236): it reported "Undone" and dropped the entry without removing anything. It now fails as `create_event` undo does (#182), and the entry stays for a retry or `discard_id`. Every undo that cannot find its item now says so with the item's title and how to drop the entry (`Cannot undo: the reminder '…' was not found under its recorded identifier …`), instead of `Reminder not found: <id>`.
- **Undo of `update_event` / `update_reminder` after a calendar or list change to another account** (#246): the record kept the identifier from before the update, which a move across accounts changes, so the undo could not find the item. It now records the identifier the item has after the save.
- **Event tools given a reminder's identifier answer not found instead of ending the server, when Reminders access is granted** (#260): given a reminder's identifier, EventKit's event lookup raises an Objective-C exception that Swift cannot catch, so `update_event`, `delete_event`, `copy_event`, `move_events_batch` and `delete_events_batch` ended the process, losing its undo history (in the batch tools, earlier rows stayed written with no undo entry). Every event lookup by identifier, undo's included, now first asks EventKit what kind of item the identifier names; a reminder's identifier gives `Event not found: <id>` (a row error in the batch tools). Without Reminders access EventKit may not report the item as a reminder, and the lookup can still end the process; a reminder's identifier normally comes from the reminder tools, which need that access. Checked on device on iCloud (reminder identifiers and event identifiers) and on Google (an event's `eventIdentifier`); other account types were not checked.
- **`delete_reminders_batch` and `cleanup_completed_reminders` record undo** (#243): neither recorded anything, so an `undo` after them restored nothing and undid an earlier, unrelated operation instead. Each call is now one undo entry holding the reminders it actually removed (after a partial failure, only those), as `delete_events_batch` does (#185), and it becomes the newest entry: an `undo` after a scheduled cleanup restores that cleanup. Like any new entry it clears the redo history, and the undo history keeps the newest 50 entries, so a frequent scheduled cleanup pushes older entries out. A call that removes nothing records nothing. One `undo` recreates the reminders one save at a time within that single call, as many as the call deleted (a cleanup in filter mode up to its `limit`, 1000 by default; every `reminder_ids` entry otherwise); until it ends, another undo or redo is refused as busy. Each comes back under a new identifier with what the reminder undo snapshot records (#228): title, list, notes and tags, priority, start and due dates, alarms, recurrence, URL and completion; subtasks are not recorded. This is the follow-up the #21 entry promised.
- **A batch undo that cannot finish no longer restores the same items twice** (#248): the undo of `delete_events_batch`, of a series delete and (since #243) of a reminder batch delete recreates its members one by one. When one failed, for example because its calendar had been deleted, the members restored before it stayed restored but the whole record went back on the undo stack, so every retry recreated them again. Now, before the first write, each member's calendar (for a reminder, its list) is checked, the calendars and lists being read once per batch and looked up the way the restore looks them up, by recorded identifier (#208, #242), so a list of the same name in another account does not count. A calendar or list that is there but does not allow changes (a read-only shared or subscribed one) does not pass either, since its save would fail part-way. When one is missing or read-only, a refresh of the store is requested and the lists are read again before the undo refuses; the refresh runs in the background, so that read may not see it yet, but every refused undo requests one again, so a later retry may find a list that was only missing from a stale view (not checked on a device). A refused batch writes nothing, and the record stays whole under the same id: it is this check that refuses the whole batch. The error says how many of the batch's items it stops and what kind of calendar or list stops them ("2 events in a calendar that is not available"), naming the items (their titles shown and capped; a shared calendar's item titles may be set by its sharer) but no calendar, list or account, since those titles can be set by someone else and an account name is often an e-mail address (#37); this is the pre-check's refusal: a member's own error inside a part-way error carries its own text, and #242's missing-list error names the list and account (#290), how many have their calendar or list in place, and that giving up with `discard_id` drops every item of the entry, including those (a partial restore is #287). A batch that also holds a delete of an occurrence and the following ones (#244) is refused by that first and discarded. If a save still fails, the record is put back with only the members not yet restored, under the same id, and the failing member is placed to run last, so the next undo restores the members never attempted first and a member that keeps failing no longer holds them back. The order does not change what a member restores: each recreates one item and reads no other member's result, a deleted occurrence too (#244). Running last helps only when the failure is not the member's calendar or list: if that is now missing or read-only, the next undo's check refuses the whole batch, and giving up the rest with `discard_id` drops every item not yet restored (#287). A member whose error is permanent would be dropped and the members never attempted kept (with none left, the record discarded); no batch member's write throws such an error today, so the tool descriptions do not mention it. After a part-way failure, the retry's text (`Undone batch (1 operation)` for one), `undo_history` and the redo instruction count only the members left. When a reminder's save reports a failure, a new store looks the reminder up, as at every site that saves a new reminder (#261): found, the save counts as done and the member counts as restored, so a retry never recreates it; when compared fields differ from what was saved, the batch answer (or, part-way, the error) names those fields for that reminder ("Restored reminder '…' — the store holds a different due, title; check it.", one entry per such reminder with its own fields, the first five, then how many more), from the names the restore returns, never from its text; a nested batch would pass its reminders' names up (no tool records one today). Not found, it is removed from the store without committing; if that removal fails it stays pending, the next member's save can write it, and a retry can write a second copy. An event has no such check: one whose save reports a failure after the store took it is treated as not written, and a retry can write a second copy (not seen on a device). The partial-failure error says a retry can add a second copy, so check first. The error says how many were restored and how many remain, names what the members it restored did not restore as they were (an occurrence's absolute-date alarm, a series recreated from its rules, #244), which the retry's text, covering only the members left, does not repeat, and gives the failed member's own error last.

## [1.19.0] - 2026-10-04

### Changed

- **BREAKING (behavior) — `move_events_batch` moves events in place** (#226): it used to copy each event and delete the original, which changed the identifier without saying so and dropped recurrence rules, attendees, coordinates and absolute-date alarms; a recurring event moved its *first* occurrence and became a one-off. Now the event's calendar is reassigned, which keeps every field. Within an account the identifier stays the same; across accounts (e.g. iCloud → Google) EventKit still moves the event, keeps its recurrence, and returns a new identifier. Only if the in-place change fails is the event copied and the original removed, and that fallback is refused when the event has recurrence or attendees. New parameters: `span` (`this` default, `all`) and index-aligned `occurrence_dates`. A recurring event with `span: this` and no occurrence date is now **refused** instead of silently moving its first occurrence; `span: all` moves the whole series. An occurrence date with `span: all` is refused rather than ignored (as is a recurring event with `span: this` and no date), whether or not the event is already in the target calendar; an event already in the target calendar is otherwise reported `unchanged` with nothing written. Every `event_ids` entry must be a string: a non-string entry is now rejected instead of silently dropped, because dropping it would pair `occurrence_dates` with the wrong event. Each result reports `method` (`in_place` / `copied` / `split` / `unchanged`), `id_changed`, `new_event_id` (only when it changed) and `not_carried_over` for a fallback copy or a split (a split occurrence lists `recurrence`: it becomes a one-off). Date-only `occurrence_dates` are read in the event's own time zone, as `delete_event` does. Undo of an in-place move moves the event back to its original calendar; undo of a split or a fallback copy restores the original, and the copy remains.

It now **refuses recurring events** (there is no `occurrence_date` on this tool; use `move_events_batch`); it used to move the first occurrence. ### Fixed

- **Pipe-deadlock bug in subprocess helpers** (#122): `Process.waitUntilExit()` was called before draining stdout/stderr pipes; `ps -A` output regularly exceeds the 64KB OS pipe buffer, blocking the child on write and deadlocking the parent's wait. Both `LiveTCCDatabaseSource` and `LiveProcessInventorySource` now read pipes via `readDataToEndOfFile()` first, then wait — child can drain naturally on stdout close. Surfaced during banner smoke-testing of #122; the unit-test suite never exercised live subprocess execution so the bug wasn't caught by `TCCDriftDetectorTests`.
- **Parent pipe write-end fd leak in subprocess helpers** (#122 verify round 3.3): The R1 fix above established read-before-wait order but missed the second half of the POSIX pipe rule: `read(2)` only returns EOF when *every* write-end fd closes, and Foundation's `Process` retains parent-side write-end handles after `run()` until the `Pipe` is deallocated. Both `LiveTCCDatabaseSource` and `LiveProcessInventorySource` now `close(2)` the parent's `stdout.fileHandleForWriting` and `stderr.fileHandleForWriting` immediately after `process.run()`, ensuring `readDataToEndOfFile` actually returns once the child exits. Local macOS 26 (Tahoe) appears to schedule fd cleanup aggressively enough to mask this; GHA macos-15-arm64 (Sequoia) blocks indefinitely without the explicit close.

### Security

- **CWE-117 stderr-injection defense in TCC drift banner** (#122 verify round 1, B1 — three-reviewer consensus): `formatBanner` was writing `runningBinaryPath` (argv[0]-derived), `recordedClient` (TCC.db-sourced), `bundleID`, ISO dates, sample-PID list, and every `skipReason` (embedding sqlite3/ps stderr + framework `localizedDescription`) directly to stderr without `EventKitErrorSanitizer.escapeForStderr`. Hostile content paths real: TCC.db is writable with Full Disk Access, and a `\r[banner] che-ical-mcp 99.99.99 — TCC OK` injection would forge a fake banner line in the operator's terminal — regressing the codebase-wide CWE-117 discipline (`EventKitErrorSanitizer.swift:144-147,219,258-271`). All interpolated values now pass through `escapeForStderr` before stderr write. Two regression tests (`testFormatBannerEscapesControlCharsInSkipReasons` and `testFormatBannerEscapesControlCharsInRecordedClient`) assert raw `\r`/`\n` cannot forge banner lines.

### Changed

## [0.8.2] - 2026-01-30

### Fixed
- **Critical: `this_week`/`next_week` week boundary calculation** - Fixed an issue where week calculations depended on system locale, causing incorrect results for users with different cultural conventions for first day of week

### Added
- **New `week_starts_on` parameter for `list_events_quick`** - Supports international week definitions:
  - `system` (default): Uses system locale settings
  - `monday`: ISO 8601 standard (Europe, Asia)
  - `sunday`: US, Japan convention
  - `saturday`: Middle East convention
- Response now includes `week_starts_on` field showing the effective week start day used
- Unit tests for week calculation with different firstWeekday settings

### Changed
- Updated MCP Swift SDK dependency to 0.10.2 (strict concurrency improvements)

### Technical Details
Previously, `this_week` and `next_week` used `Calendar.current.firstWeekday` without explicit control. This caused:
- Users expecting Monday-start weeks (ISO 8601) to get Sunday-start results on US-locale systems
- Inconsistent behavior depending on system locale

The fix allows explicit control while defaulting to system locale for backwards compatibility.

## [0.8.1] - 2026-01-25

### Fixed
- **Critical: `update_event` time validation bug** - Fixed an issue where updating only `start_time` without `end_time` could result in an invalid event state (startDate > endDate), causing the event to become unsearchable or invisible in the calendar
- When only `start_time` is provided, the event's original duration is now automatically preserved
- Added explicit validation to reject events where start time is not before end time (for non-all-day events)

### Added
- New error type `invalidTimeRange` for clearer error messages when time validation fails
- Improved `update_event` tool description with clearer documentation about time handling
- Added `all_day` parameter to `update_event` tool for converting between timed and all-day events
- Unit test framework with time validation tests

### Technical Details
The bug occurred because `startDate` and `endDate` were updated independently. When moving an event from Jan 25 to Jan 31 with only `start_time`, the event would have:
- `startDate`: Jan 31, 14:00
- `endDate`: Jan 25, 15:00 (unchanged from original)

This invalid state caused EventKit to handle the event incorrectly. The fix preserves the original event duration when only the start time changes.

## [0.8.0] - 2026-01-16

### Changed
- **BREAKING**: `calendar_name` is now **required** for `create_event`, `create_events_batch`, and `create_reminder`
- Removed implicit default calendar behavior to prevent events being saved to unexpected calendars
- Improved error messages guide users to use `list_calendars` to see available options

### Why This Change
Previously, if `calendar_name` was not specified, events/reminders would be saved to the system's default calendar. This caused confusion when users had multiple accounts (iCloud, Google, Exchange) and didn't know where their data went. Now the API explicitly requires specifying the target calendar.
