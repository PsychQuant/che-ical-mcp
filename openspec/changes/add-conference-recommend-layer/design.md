## Context

#346 的診斷（2026-10-26）列出推薦層與標準層的五個衝突（C1–C5）與三個比對方案（A 存標準標題、B 先還原、C 標記裡放識別碼）。PR #498（#351）當時在改 `conference.md` 第 4、6、7 節，已於本變更之前合併。

## Decisions

### 比對：存標準形式，標準流程讀標準形式（方案 A，不改標記）

推薦過的事件把自己的標準標題、標準地點、加標記的行號存在 notes 最上方的區塊；標準流程的每個比較與寫入、以及 `create_event` 之前的重複搜尋都讀標準形式。這樣重貼不落到對照表（C1）、關掉推薦不依賴議程文字沒變（C2：還原寫的是區塊裡存的標準形式）、區塊不會被當成使用者文字移到標記下面（C3）、標記可以精確去掉（C4）。

不選 B：每次執行即使沒變也要寫兩次。不選 C：會改到 v1.21.0 事件已經帶著的標記格式，而且識別碼解決不了還原標題（C2）。

項目識別碼是 `conference-recommend-item:` 那一行（標準標題加起始），不依賴顯示的標題。行裡的起始與事件實際起始不同（使用者在行事曆手動移過）就不算格式正確，推薦層不寫，標準流程把它當成「被別的層改過標題的事件」送到既有的對照表；配對時用 item 行裡的標題（比較用標題，`conference.md` 開頭段定義，只用於帶本模組標記對的事件），所以手動移過的事件仍配得上自己的項目，不會變成「不在這組裡」。這種事件不算完全相符，一定進對照表。

區塊只由列舉的行構成；begin 與 end 之間有其他行（例如使用者打的一行）就不算格式正確。丟棄區塊時只丟列舉的行，其他行照「Whose text is whose」移到標記下面，不刪。

### 為什麼還是需要標準形式的比對：伺服器的略過擋不住

`create_event` 只在同標題時略過；推薦過的事件標題不同，所以伺服器會再建一個（2026-11-09 實測，見 tasks 3.1）。防止重複的是標準形式的比對，不是伺服器。

### 模式

設定檔欄位叫 `conference_mode`，不叫 `mode`：那份設定檔的鍵是平的、每個模組一個（`conference_module`、`lodging_module`），單獨的 `mode` 看不出屬於誰。推薦只在三種情況下拿掉：這次的訊息要求、使用者對推薦問題回答移除、使用者對寫明推薦會拿掉的對照表列回答 yes。模式因設定檔或預設而是 `standard`，或 `recommend` 模式沒給推薦而標準流程要改某個推薦過的時段時，先問一次（移除或保留）；沒人回答就保留、列為待答。這樣一次性的推薦不會在之後的普通重貼裡被悄悄拿掉，呼叫者寫的理由也不會在沒人同意時消失（verify 第 2 輪）。

### 與 #498 分開

契約放新檔；`conference.md` 改開頭段落（標準形式與比較用標題）、第 7 行的解析清單，以及第 6 節的兩處（「Whose text is whose」加上區塊行的例外、Always 加上建立前的客戶端比對）；報告的新行寫在推薦層檔案裡（「加在 `conference.md` 第 7 節第 3 行之後」），不改第 7 節本身。

### v1 的範圍（verify 第 3 輪收窄）

第 3 輪的六個 MEDIUM 都出在推薦層碰到標準模式的邊緣（沒有議程的訊息、還沒回答的列、候選組、別組的事件）。逐條補會再開新的邊，所以 v1 收窄成這些情況不會發生：推薦層只在帶議程、觸發會議模組的那次執行裡跑；只寫完全相符、沒有任何列點名、而且決定組或行事曆的問題都已回答的場次（或這次新建並讀回的場次）；還原只寫存著的標準形式加上標準流程這次自己的完全相符更新，不自己改標題或起始；被列點名的推薦事件由那一列處理，列的文字寫明 yes 會拿掉推薦，候選組 yes 時它跟其他場次一起換新標記；客戶端比對讀每一組的模組事件。只給推薦或只說移除的訊息不在 v1。

## Risks

- 使用者手改區塊會讓推薦層停手（列出、不寫），要靠對照表回到標準形式。
- 「手機月檢視一眼看得懂」只能在裝置上看，契約證明不了。
