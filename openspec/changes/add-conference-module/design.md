## Context

plugin 是純 markdown 加 shell。三個建立事件的入口各自建單一事件；#337 已合併，`plugin/rules/calendar-routing.md` 定義了設定檔查找、分類與 `Routed to …` 報告行。維護者為一場三天的研討會（2026 年 10 月）手工建出的形狀是本模組的原型：一個跨三天的全天事件、notes 寫逐日總覽，加每個時段一個場次事件，同時段不同會場的場次合成一個事件。

四個待定點由維護者在 #338 討論中定案（去重鍵、已報名名單、關閉鍵名、結束日實測）。其中兩點是維護者明確回答的：標題改了的場次當新事件並提醒（2026-10-24），以及場次的比對鍵是標題加起始時間、模組要建立提醒（2026-10-25）。其餘為建議且無異議。由這些答覆推導出來的設計（時間更正與標題更正先列對照表、同意後更新舊事件；提醒的預設值）是實作者的，不是維護者講的。

## Goals / Non-Goals

**Goals:**

- 議程進來就建出同一種兩層形狀，與入口無關。
- 重貼或更正議程不產生重複事件，也不改寫不屬於模組的事件。
- 日曆由 #337 路由決定，整份議程只解析一次。

**Non-Goals:**

- 旅程私人行程、其他模組、持久化名單、自動刪除或移動事件。

## Decisions

### 模組是一份契約檔，不是程式

`plugin/rules/event-modules.md` 說明模組的形狀（觸發條件、版面、去重鍵、報告行）與各模組共同的三條規矩，並索引各模組；`plugin/rules/modules/conference.md` 是會議模組的契約。三個入口各加一句「輸入符合索引裡某個模組的觸發條件時照模組做」，不寫模組名，所以新增模組不必改入口。理由：模組的核心是模型對議程的分類與版面，沒有可決定性的程式碼可寫；一份契約加實例是唯一能讓三個入口一致的方式。

### 去重標記放在 notes，不另建狀態檔

議程沒有 `archive-event` 那種穩定的來源 ID（Message-ID），所以不用 `state/archives.json` 當去重依據。每個事件的 notes 含兩行連續的整行標記（`conference-module: <正式名稱> | <起日>` 與 `conference-module-item: umbrella|session`），只有含這兩整行的事件才算模組事件；句子裡提到 `conference-module:` 不算。標記以上是模組的文字、更新時可改寫；標記以下是使用者的文字、每次更新都保留（第 3 輪驗證後由「必須是最後兩行」改成這樣：使用者最常見的手動修改是在 notes 末尾加字，原本的寫法會讓事件從此不被認出、下次重貼就重複）。替代方案：另建 `state/conferences.json` → 多一份要同步的狀態，且事件被手動搬動後兩者不一致，被拒絕。

### 比對鍵是標題加起始時間（維護者 2026-10-25 在 #338 定案）

第 1 輪實作曾改成「標題加起始日期」，讓時間更正能靜默更新；維護者 2026-10-25 定案改回「標題加起始時間」。理由：以日期比對時，同一天兩個同名時段（例如上午、下午各一個「休憩」）會被當成同一個事件。代價是時間更正不再靜默：起始時間改了的場次與標題改了的場次一樣，走對照表請使用者確認一次，因為模組無法分辨「這場改時間」與「另一場剛好同名」。

### 找既有集合的三步

先在路由到的日曆找標記並依標記分組。名稱與起日都相同的那一組單獨使用；沒有的話，名稱相同、或起日相同且至少一個場次（開幕、閉幕、休息與用餐除外）的標題與起始時間相同的組才算候選，同一天開始的另一場會議不算（第 4 輪驗證；PR #498 第 3 輪加上除外）。路由日曆裡沒有完全相符的一組、也沒有候選，就跨所有日曆唯讀找一次，路由日曆裡有同日組也照找（第 3 輪驗證指出：原本「一筆都沒有才跨日曆」會被別場會議的標記擋住；PR #498 第 3 輪：同日組也不能擋）；找到的在找手建事件之前先問一題，這一題只決定這次用哪個日曆（用那一組的日曆、留在路由日曆並不再問那一組、或停止），套不套用由對照表那一題決定。接著在這次的日曆裡、議程那幾天找手建事件：沒有集合時全部找，有集合時只為集合缺的項目與缺的總覽找；收進標題含會議名稱的事件，以及落在集合缺的項目時段上的有時間事件。（已被〈採納從 v1 拿掉〉取代，只留作紀錄）手建事件只能經對照表、使用者同意後「採納」：加上標記、把模組的 notes 放在標記之上（原本的 notes 放在標記之下不動）、並把標題改成模組的寫法，下次重貼才對得上；對照表事先列出新舊標題。採納不動提醒。使用者拒絕採納時，同名同時的項目不建立（`create_event` 會略過），報告記為 kept；下次重貼會再問。`create_event` 回 `skipped` 只表示伺服器找到同名同時的事件，不表示模組擁有它，所以沒有標記就不寫入（第 3 輪 HIGH）。

#351 在拋棄式日曆上實跑（2026-11-09，repo build 的 binary 經 `--cli`）後補的四處：(1) 拒絕採納後模組會建出其餘事件，第二次重貼就找到完整的一組，第 3 步原本只在「沒有集合」時跑，手建事件再也不會被問；改成有完整集合時也對它缺的項目與總覽找手建事件。(2) 正式名稱與簡稱都改了、起日不變時，舊的一組不是候選，原本會靜默再建一組；改成：起日相同、而且有場次與議程重疊（去掉各自簡稱與（未報名）後標題相同，或同一日期與時間；開幕、閉幕、休息與用餐不算，不相干的同日會議都有這些）的舊組，在對照表那一次提問裡一併問是不是同一場改名，附對照表；沒有重疊的同日會議不問；有幾組重疊就在同一題全部列出，免得先問的那組答 no 後，真正改名的那組沒被問到。沒人能回答時什麼都不建、不寫（新的一組在改名時就是重複），報告列為待決並點名舊組；之後每次重貼，只要重疊的同日組還在、議程還沒有完整集合，就再問一次。答 yes 讓舊組成為完整集合，答 no 讓新的一組建立，此後它就是完整集合，所以不必另存「答過了」的狀態。手建事件不再讓這一問被跳過，而是當成逐項的採納列。(3) 採納只寫標記、notes 與標題，手建總覽若以最後一天為結束（少一天）就一直少一天；改成採納時一併寫議程的時間、日期與地點，完整集合的總覽日期不同也算更新。(4) 帶會議時區 `display_timezone` 讀全天事件，日期會隨時區差位移（台北主機、紐約會議：3/8–3/10 讀成 3/7 11:00 起），所以全天事件的日期一律從不帶 `display_timezone` 的讀取取得。衝突檢查原本沒寫範圍；維護者定為查所有日曆（不帶 `calendar_name`），因為依路由，航班、住宿在旅遊日曆、課程在各自的日曆，只查路由日曆會漏掉報告要抓的衝突。另外（PR #498 第 2 輪驗證後，原則：不確定的選擇就不寫、去問，沉默不建出可能重複的東西）：第 2 步選了別的日曆裡的那一組，該日曆就是這次的日曆，手建事件的搜尋、採納、建立與讀回都用它，只有衝突檢查查所有日曆；第 3 步略過帶任何模組標記的事件（採納它會讓 notes 有兩組標記，事件從此脫離集合），並多收「日期與起始時間等於某個集合還沒有事件的項目」的未標記事件；手建事件能對到項目（同標題或同時段）就提為「採納？→ 該項目」，對不到才寫「沒有項目」；每個項目在表裡最多一列，舊事件與手建事件同時對到時，在那一列並列兩者讓使用者擇一；同標題配對先把完全對上的從兩邊拿掉，剩下的依日期時間一對一；拒絕採納時，項目照常建立（使用者說那不是這個項目），只有手建事件同標題且涵蓋起點（`create_event` 本來就會略過），或是被提為總覽的全天事件（旁邊再建一個總覽就是重複）時，項目不建、記為 kept，下次重貼再問；完整集合裡缺的項目一律列在表上問要不要建，因為模組分不出議程新增與使用者手動刪掉；沒人能回答時，表上每一列都列為待決、不寫，表上有集合層級的列就什麼都不建；衝突檢查在對照表答完之後跑，略過對照表對到的舊事件（已被下方 PR #498 第 8 輪取代：只略過答 yes 的列對到的舊事件）。已知限制：正式名稱、簡稱與起日都改了的議程，三類都對不上，會另建一組，舊組不列出。PR #498 第 4 輪：第 2 步只決定日曆，改名提問一律在對照表那一題，第 2 步留在別的日曆的那一組不再問；手建事件的列有固定的答案（提案列：採納、另建這個項目、都不是；只靠名稱的列：是哪一項、總覽、或都不是；多個事件對同一項：選一個、另建、或都不要），拒絕採納不會自己建出項目；集合層級的列沒答時，其他列一律待決、什麼都不寫，免得採納寫上新標記把舊組藏起來；有集合時第 3 步只收能提給集合缺的項目的事件；只剩一行標記的事件被採納時，舊 notes 裡開頭是 `conference-module` 的行前面加上 `· `；單純的 yes 只回答是非列，要選擇的列等使用者選。**v1 的退路**：若第 5 輪仍在採納上找到漏洞，就把採納從 v1 拿掉：刪掉手建事件各列的「採納」答案與〈Adoption〉段，手建事件只列出、不採納，其餘規則不變。PR #498 第 3 輪：對照表上沒回答的列是待決、不是 no，只寫使用者明確回答的列；配對分三輪（同標題、去掉各自簡稱後同標題、同日期與起始時間），改名與改標題的場次才配得起來；同日重疊只看去掉簡稱後的同標題，單看時間要兩個以上場次相同才算；改名提問的答案只能是一組或都不是；只靠名稱收進來、對不到項目的手建事件要問「是哪一項、總覽，還是都不是」，回答前它可能對應的項目（全天事件是總覽，有時間的是同一天的項目）不建；完整集合缺總覽時總覽也列「不在集合裡 → 建嗎？」；這類列答 no 不留狀態，之後每次重貼都會再問，報告寫明怎麼讓它停；只跳過帶本模組完整兩行標記或其他模組標記的事件，只剩一行的仍是手建事件；改名答 yes 才改用議程的標題，其他情況沿用集合標題的簡稱；衝突檢查也略過這次採納的手建事件。

### 採納從 v1 拿掉（PR #498 第 5 輪，2026-11-09）

**上兩段（〈找既有集合的三步〉的本文與 #351 那一段）裡關於採納的句子（採納、名稱列、多事件列、拒絕採納時的建立規則、只剩一行標記時的跳脫、採納時寫入時間與日期）已被本段取代，只留作紀錄。**

第 2 到第 5 輪驗證每一輪都在手建事件的採納上找到新的漏洞：「都不是」的意思前後不一、多個事件併成一列時繞過了重複防護、有集合時第 3 步收不到只靠名稱的事件、採納時沒處理全天與有時間的轉換和重複事件的 span、只剩一行標記時跳脫範圍與共用規則不一致。依第 4 輪記下的退路，v1 不採納手建事件：

- 第 3 步找到的手建事件（依名稱或時段）**一律不採納、不改名、不寫入**，只在對照表裡列在它可能對應的項目或總覽旁邊；一個事件只有在它可能對應的每一個項目都已有事件時才不收。
- 每個這樣的項目一列是非題：「找到手建事件 X；仍要建立這個項目嗎？」答 yes 在旁邊建立、事件不動；答 no 不建立，只要仍然適用，之後每次重貼都再問；沒答是待決、不建立。
- 會讓 `create_event` 略過或建出重複的地方不問建立：列出的事件標題與項目相同且涵蓋起點，或總覽旁有標題就是正式名稱的全天事件。這時項目不建、記為 kept，報告寫出佔位的事件。標題只是含正式名稱的全天事件（例如「… Day 2」）照常問，因為伺服器不會略過，旁邊建總覽也不重複。
- 舊事件與手建事件對到同一項目時，那一列是舊事件的列，並列出手建事件；答 no 時只有在可以建立的情況下才建立。
- （已被下方 PR #498 第 6 輪的 (2) 取代：改成在路由日曆重跑整個找既有集合的流程）第 2 步選了別的日曆裡的那一組、對照表卻說它不是這場（集合層級答 no，或改名提問答都不是）時，新的一組建在**路由日曆**：先在路由日曆重跑第 3 步、問完它的列再建立，報告第 1 行寫明。

PR #498 第 6 輪補的四處（同一原則：不確定就什麼都不寫、先問）：(1) 舊事件的時間或標題更正會落到手建事件佔住的時段時，那一列說明並問「仍要更新嗎？（同一時段會有兩個事件）」，要單獨回答，未答是 pending，答 no 舊事件不動；(2) 跨日曆選的那一組被否決後，回到路由日曆把整個找既有集合的流程（第 1 步配對與它的集合層級列、改名提問，然後第 3 步）重跑一次再建，第一張表的回答作廢重問；(3) 同一日曆裡集合層級答 no 或改名答都不是之後，第 3 步對整份議程（含總覽）重跑再建新的一組；(4) 表裡列出的手建事件不從衝突檢查拿掉，另列一行「表裡已列的衝突」。手建列與「仍要更新嗎」列都不被一個籠統的 yes 回答。

PR #498 第 7 輪補的：總覽要改日期或標題時，也為它新的日期找手建的全天事件，列出的話總覽那一列問「仍要更新嗎」、要單獨回答（完全相符組的總覽改日期、候選組答 yes 時都算）；只列一組的改名提問，籠統的 yes 不回答它，要點名那一組或對改名提問本身答 yes；舊事件那一列只要點名了手建事件就要單獨回答，並寫明 no 會做什麼；同一日曆的重跑也讓第一張表的回答作廢重問；別組的模組事件佔住同名時段時不提供建立，記為 kept 並在報告點名。

PR #498 第 8 輪補的（同一原則；第 8 輪起，只有照文字做會在沒有明確 yes 時寫入、或造成資料遺失或重複的問題才算擋）：(1) 選擇列同時列出好幾組（幾個候選組、幾個同日組、或候選組加同日組）時，先單獨問是哪一組或都不是；配對、第 3 步的手建搜尋、「不在集合裡」與手建列都要等選定之後，只對選定的那一組算出來再問，沒人能回答就全部待決、什麼都不寫。原本照某一組算的列，答另一組時可能把同一項建成兩個事件、也可能漏掉另一組缺的項目。Match 第 3 條「幾個候選組就問是哪一個」併進同一個選擇列。(2) 第 2 步只在別的日曆找到集合時才問，沒找到就不問、直接用路由日曆。(3) 衝突檢查只略過答 yes 的列對到的舊事件，五處文字一致；答 no 的更正留下的舊事件若與新場次重疊，照樣報告。(4) 籠統的 yes 不回答的列加上「點名手建事件的舊事件列」；改名提問點名那一組只回答這個選擇（以及和它一起列出的舊事件 → 項目列），「不在集合裡」與手建列要另外回答；候選組的總覽在「仍要更新嗎」答 no 之後留在舊標記下，報告寫明，來源不對應到任何事件。

為什麼延後而不是繼續修：採納要把使用者自己的事件改寫成模組事件，牽涉標題、時間、全天轉換、重複事件、舊 notes 的跳脫與標記；每補一處就多出新的組合。只列出、問要不要另建，使用者的事件永遠不會被改，代價是使用者得自己刪掉手建事件或答 no。**v2 待辦**：重新設計採納；以及「記住的拒絕」（使用者標記某個議程項目不要，之後重貼不再問；目前答 no 的列會一直回來，第 5 輪 LOW 13）。

### 總覽用純日期（第 3 輪驗證，2026-10-25 實測）

全天事件是浮動日期，以 host 的時區解讀；帶 offset 的時間是一個瞬間，不是一天。實測：host 在 `+09:00`，`2026-11-10T00:00:00+10:00` 讀回成 11/9 起；純日期 `2026-11-10` 到 `2026-11-13` 讀回 11/10–11/12。先前的實測都在 host 時區等於會議時區時做，所以測不出來。契約改成純日期，結束日用最後一天的隔天（排他邊界）。讀回時比對 `start_date_local`／`end_date_local` 的日期，不比對 UTC 的 `start_date`：在 UTC 以東的 host 上，全天事件的起點印出來是前一天（第 4 輪驗證）。不符就在報告警告並先問，不再自動重送同樣的值（重送改變不了結果）。`create_event` 回 `skipped` 時，總覽是別人建的事件，只能經採納處理。

### 時間寫法

場次的起訖寫成會議當地時間、不帶 offset，再加 `timezone`；伺服器以該時區解讀，夏令時間也由伺服器處理，模型不必自己算 offset（第 4 輪驗證；實測 Berlin 夏令時間結束隔天的 10:00 存成 UTC+1）。`update_event` 寫時間時同樣要帶 `timezone`，起訖一起給：實測在 JST 主機上不帶 `timezone` 更新成 `14:00`，Berlin 的場次變成 06:00（第 5 輪驗證）。`check_conflicts` 沒有 `timezone` 參數，所以給它帶當天 offset 的當地時間，這是唯一需要 offset 的地方。讀回場次用 `display_timezone` 設成會議時區；總覽是浮動日期，不設。重貼時沿用既有那一組標題裡的簡稱與時段寫法，換入口或換 session 重貼也能完全對上。

### 場次一律用 `create_event` 逐一建立

`create_events_batch` 的每項 schema 沒有 `alarms_minutes_offsets`（handler 傳 `alarmOffsets: nil`），而它的說明寫 PREFERRED、`calendar-management` 也把多事件導向它；用它建場次，提醒會靜默消失。契約與索引都寫明模組逐一用 `create_event`。

### 提醒：建立時設定、只在報名狀態改變時更新（維護者 2026-10-25 在 #338 要求）

維護者要求模組建立提前幾分鐘或幾小時的提醒。預設值是實作者給的，不是維護者講的：出席的場次 15 分鐘前；自己的發表 60 與 15 分鐘前；「（未報名）」的場次不設。同一則訊息裡使用者說了別的提前時間就照他說的。`update_event` 的 `alarms_minutes_offsets` 會整組取代，所以一般的更新不動提醒，使用者手動改過的提醒才不會被重貼蓋掉；唯一的例外是報名狀態改變（去掉前綴就設出席場次的提醒，加上前綴就清掉），否則改成出席的場次會沒有提醒。工具讀不回提醒，所以報告寫「設了什麼」，不寫「讀回什麼」。

總覽不由模組加提醒。實測發現行事曆會替新建的全天事件加上使用者自己設定的預設提醒（前一天 09:00），傳 `alarms_minutes_offsets: []` 給 `create_event` 也一樣，只有事後 `update_event` 傳 `[]` 才清得掉。這是使用者自己的行事曆設定，模組不去蓋掉它，報告註明可能有這個提醒。

### 邊界輸入先問

單一會議的時間議程與工作坊、一天的研討會，文字上切不開（第 4、5 輪驗證）。所以把「項目」定義成議程或時間表給了自己標題與起始時間的那一項，並規定：只有一天、而模組判斷會觸發的輸入，除非使用者自己說了是會議或議程，先問一次要建成議程還是一個事件，照答案做。觸發本身仍是模型判斷，這個問題是防止把一場會議讀成議程的保險。

### 只更正部分項目的訊息

「某場改到 14:00」這種訊息本身不滿足觸發條件，也沒有會議名稱與起日。所以觸發條件以討論串或既有那一組持有的議程判斷；`archive-event` 經 `state/archives.json` 找到總覽，用總覽的標記找到那一組，只改被點名的項目，不把其他項目列為過時，也不把某個項目的值寫進總覽。對應表指到的事件若帶總覽標記，就是模組自己的對應，不必再問；沒有標記才是模組之前的單一事件，先問。伺服器沒有依 id 讀事件的工具，所以用 `search_events`（狀態檔記的日曆、關鍵字 `conference-module-item: umbrella`）找出那個 id。還沒有任何一組時，以討論串的完整議程套上更正後再建立。

### `create_event` 的略過條件

伺服器的去重是「同一個日曆裡、同標題、且既有事件涵蓋新起點前後 30 秒」，不是「同起點」（第 5 輪驗證核對原始碼）。所以：被略過時比對那個事件的起點；同起點、同一組的模組事件才算未變；沒有標記的是手建事件，只列出、不寫入，項目記為 kept；其他情況（別組的事件、或起點不同，例如拒絕時間更正後舊事件仍涵蓋新起點）項目不建立，報告記為 kept 並寫出佔位的事件。同一天背對背、標題相同的兩個項目會互相擋住，所以標題各加起始時間。

### 標記名稱與「未變」

標記裡的名稱是正式名稱把 `|` 改成 `／`、換行改成空格；比對時議程的名稱也做同樣的轉換，否則名稱含 `|` 的會議每次重貼都對不上。「未變」以議程推得出的欄位判斷（標題、起訖、地點、該項的議程文字）；notes 只在議程文字變了才改寫，改寫時把標記上方使用者加的行移到標記下方，不丟。

### 複製的文字不能形成標記

標記改成「含兩整行」之後，複製進 notes 的議程文字若剛好有兩行長得像標記，就會被當成標記（第 4 輪驗證）。所以複製的文字裡以 `conference-module` 開頭的行前面加 `· `，而且 notes 裡有超過一組標記的事件不算模組事件。

### 自己的發表

只認輸入裡標成使用者的、或使用者在同一則訊息裡說的那一項，不從題目猜；沒有就當作沒有。它一律是獨立事件，即使在平行時段裡也一樣（時段事件仍列出每個會場）。

### 會議名稱的三個位置

總覽標題與標記用正式名稱（標記是比對用的，必須穩定）；場次標題用議程或使用者慣用的簡稱，沒有簡稱才用正式名稱（手機月曆一格放得下）。標記裡的 `|` 寫成 `／`，換行寫成空格，免得名稱弄壞分隔。

### 結束日以實測為準

實測（2026-10-25，iCloud）：結束日為最後一天的隔天（排他邊界）讀回為最後一天 23:59:59；以最後一天自己當結束會少一天。契約用排他邊界，建立後讀回並與議程比對。

### 路由只解析一次

模組先對整份議程以 `calendar-routing` 解析一次，結果套到總覽與所有場次。總覽（全天、沒有時間）不符合典型的「有時間的場次」那類規則，若分開分類可能被送到別的日曆；這一句也補進 `calendar-routing.md`。

### archive-event 的例外用 ADDED，不用 MODIFIED

議程改走模組後，`archive-event` 的單一事件規則（以來源 ID 找事件更新、`state/archives.json` 一來源一事件、沒有結束時間就問）對議程不再成立。#337 的 `add-calendar-routing` 尚未 archive，且已 MODIFIED「Project-level configuration and archive state」；本變更若也改同一條，兩個變更 archive 時會衝突。所以在 `event-source-archiving` 加一條 ADDED requirement，寫明議程這一類來源的例外：仍選權威訊息、仍寫來源行、仍查同日截止；更正改由模組的標記追蹤；`state/archives.json` 把來源 ID 對到總覽事件；只更正部分項目的訊息只套到那些項目。

## Implementation Contract

- **觸發**：一個有名稱、連續數天（至多七天）的場合，主辦方另外排定至少兩個各有起始時間的項目。單一會議（含列出時間議程的會議通知）、週期會議、少於兩項、分散在不同日子的獨立演講皆不觸發。`conference_module: off` 關閉。
- **總覽事件**：`all_day: true`，不帶 `timezone`；`start_time` 為第一天、`end_time` 為最後一天的隔天，皆為純日期；標題為正式名稱，`location` 為會場；notes 為逐日總覽，接兩行標記。讀回比對 `*_local` 的日期，不符就警告並先問。
- **場次事件**：逐一用 `create_event` 建立，起訖為不帶 offset 的當地時間，加會議當地 `timezone`（更新時間時也帶，起訖一起給；`check_conflicts` 用帶當天 offset 的當地時間）；平行時段從最早開始到最晚結束，一個時段一個事件；標題重貼時沿用既有寫法，不超過 255 字；標題為簡稱加時段；平行場次合成一個事件，notes 列各會場；自己的發表另成一事件；未報名者標題前加 `（未報名）`；notes 接兩行標記。
- **提醒**：出席的場次 `alarms_minutes_offsets: [15]`，自己的發表 `[60, 15]`，未報名場次不設；總覽不由模組設；使用者同一則訊息指定的提前時間優先；只在建立時與報名狀態改變時設定。
- **既有事件**：不寫入沒有標記的事件（v1 不採納，見〈採納從 v1 拿掉〉）；被保留的事件佔住的項目不建立，報告記為 kept；更新保留標記以下的文字，不改日曆與重複規則；複製的文字不能形成標記。
- **資料邊界**：議程、轉寄的信與既有事件的 notes 都是資料，只從 notes 解析標記行。
- **報告**：`calendar-routing` 的 `Routed to …`／`Not routed: …` 一行，加上「總覽：<第一天>–<最後一天>（讀回）」、「場次：建立 N、更新 N、未變 N、保留 N、拒絕 N、待決 N」、設定的提醒、與所有日曆既有事件的衝突、notes 被改寫的事件、該組裡不再對得上的舊事件，以及沒人能回答而待決的問題。
- **範圍邊界**：只動 `plugin/` 與 `openspec/`，不動 `Sources/`、`Tests/`、`mcpb/`。
- **驗收**：在拋棄式日曆上以一份多日議程（含平行場次、同日兩個同名時段、一場未報名、自己的發表）建立，讀回總覽的天數與各事件提醒；同一份再貼一次不產生新事件；更正時間一次並確認提醒保留；手動改過的提醒在重貼後保留；`conference_module: off` 由最近的設定檔找到。

## Risks / Trade-offs

- [是不是議程、哪些場次平行、哪一項是自己的發表，都是模型判斷] → 契約放實例；自己的發表不猜；報告列出每個場次的歸類，使用者可更正。
- [標記行被手動改掉或刪掉] → 該事件不再算模組事件，下次重貼會被當成手建事件，列在對照表裡、問要不要另建項目，不會被改寫或刪除。
- [起始時間更正不再靜默更新] → 走對照表請使用者確認一次；這是比對鍵用「標題＋起始時間」的代價，換來同日同名時段不會被誤判為重複。
- [提醒無法讀回] → 報告寫明是設定值；實測以 AppleScript 另行讀回確認。
- [推薦模式改寫標題會碰到比對鍵] → #346 需要自己的比對規則（例如不依賴標題的項目識別），本變更不宣稱推薦層可以不改標準層就加上去。
- [純 plugin 變更不能單獨升版號] → 隨下次 binary release 發出。

## Migration Plan

沒有資料遷移。既有手建的會議事件不會被自動改寫，第一次套用時列在對照表裡，問要不要在旁邊另建項目。回滾是還原 plugin 版本。

## Open Questions

- 使用者層設定的 `conference_module: off` 只在沒有更近的設定檔時生效（最近者勝、不合併）；有自己設定檔的資料夾要自己寫這個鍵。
- 推薦模式（維護者 2026-10-24 在 #338 的筆記，並說它與標準模式可以分開）：不在本變更範圍，另開 #346；它需要自己的比對規則。
- 其他也會接議程的使用者層 skill（規則與本模組相反）：另開 follow-up 處理採用與優先序。
