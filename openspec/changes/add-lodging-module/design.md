## Context

plugin 是純 markdown 加 shell。#338 已建好模組機制：`plugin/rules/event-modules.md` 規定一個模組要定義觸發條件、版面、去重鍵、報告行，並索引各模組；會議模組（`plugin/rules/modules/conference.md`）是目前唯一的條目。三個建立事件的入口（`archive-event`、`/quick-event`、`calendar-management`）都寫成「輸入符合索引裡某個模組的觸發條件時照模組做」，所以加模組不必改入口。#337 已讓日曆由資料夾的路由決定。

維護者 2026-10-27 回覆「Clarity 全照建議」，定了三件事：住宿事件只標住宿的夜晚（結束日是退房日、不含，退房時間寫 notes）；沒有確認信的住宿，只有輸入明確給了日期與地點才建，標「（未確認）」；沒訂房的夜晚只在回報說。2026-10-29 的 `/spectra-discuss` 又定了五件事：標記鍵是訂房編號；取消時**先問再刪**（維護者明確選的）；多房間一單一事件；`location` 放地址、旅館名放標題；一則訊息符合兩個模組時各建各的。其餘（標記的具體寫法、報告行文字、未確認住宿的升級流程）由診斷提出、無異議，屬實作者的設計，不是維護者講的。

會議模組與住宿模組沒有共用的事件或鍵：會議模組擁有主辦方排定的項目，住宿模組擁有使用者自己的住宿（`conference.md` 明寫不替使用者建住宿）。

## Goals / Non-Goals

**Goals:**

- 一封訂房確認信、變更通知或取消通知，對應日曆上**一個**住宿事件，且後續信件找得到它。
- 取消能把事件移走，但不在使用者不知情時刪東西。
- 多個模組能在同一則輸入上共存而不互相覆蓋。

**Non-Goals:**

- 行程變更後的自動檢查（#341）、旅館以外的類別、為未訂房的夜晚建事件、任何提醒、拆事件。

## Decisions

### 住宿模組是第二個契約檔，沿用四部分

`plugin/rules/modules/lodging.md` 依 `event-modules.md` 的四部分寫：觸發條件、版面、去重鍵、報告行。與會議模組不同處只有四處（一個事件而非兩層、鍵是訂房編號、會取消、沒有時區也沒有提醒），其餘一律引用而不重述：日曆解析一次、`create_event` 逐一建立、輸入文字是資料、採納手建事件走對照表加明確同意、`lodging_module: off`。理由：兩份契約各自重述共通部分，之後只會分歧。

### 版面：一個全天事件，結束日依呼叫而定，每次寫入後讀回

全天事件是浮動日期，以 host 時區解讀，起訖皆為純日期，不帶時間或 offset。2026-10-29 在裝置上（iCloud、host +09:00）實測，同一個純日期結束日有兩種讀法：`create_event` 與「定時事件轉全天」的 `update_event` 把它當排他（結束 11-13 讀回 11-12），已經是全天的事件做 `update_event` 則把它當包含（結束 11-15 讀回 11-15；一夜的住宿用起訖同一天可行）。可能的原因是 server 設定日期時事件是否已是全天，這是從賦值順序推的推論，不是文件保證，也沒量 Google 與 Exchange。所以契約這樣寫：create 傳退房日；對已是全天的事件 update 傳最後一晚；採納定時事件轉全天時傳退房日；**每次寫入日期之後都讀回**，比對 `start_date_local` 的日期與入住日、`end_date_local` 的日期與最後一晚，不符就說並以一次更新補正，補不好就停下來問。會議總覽的 update 有同樣的暴露（#364）。

標題 `<旅館名> <N> 夜，<退房日> 退房`；`location` 是街道地址，缺就留空，**不**拿旅館名補，因為地圖與導航會讀它。notes 由上而下：入住時客人要帶或要做的事（自成一行，照確認信抄）、訂房編號、入住時段、退房日與時間、房型與方案、金額與是否已付、取消條件、來源行、標記行。最上面放「客人在櫃台要做的事」是因為診斷中的實際案例（入住時要出示或簽署的東西）就是這種資訊被丟掉。**不抄任何祕密**（信用卡號或其一部分、PIN、門鎖或鑰匙盒密碼、一次性或登入碼、密碼、管理訂房的 PIN），這條壓過第一行的「照確認信抄」：入住行含祕密就抄去掉祕密的版本並在報告說明。notes 的自由文字另限 300 字、不留連結。金額與是否已付只是來源日當下的快照。訂房編號是確認信稱為 reservation／booking／confirmation number 的那個，不拿 PIN 或密碼當鍵，分不出來就問。

### 去重鍵與標記：訂房編號

notes 內一行整行標記 `lodging-module: <訂房編號>`（編號中的 `|`、換行、前後空白照會議模組的規則正規化）。只有 notes 含這一整行恰好一次的事件才算模組事件；句子裡提到該字樣、引用文字裡出現的都不算；複製進 notes 的文字若有以 `lodging-module` 開頭的行，前面加 `· `，所以只有模組自己寫的那一行是標記。標記以上是模組的文字、更新時可改寫；以下是使用者的文字、更新時保留。找法：`search_events`，關鍵字 `lodging-module:`，明確範圍（入住日前 60 天到退房日後 60 天），不帶 `display_timezone`（全天事件是以 host 時區為準的浮動日；2026-10-29 在 +09:00 主機實測，`Asia/Taipei` 讓 start 讀成前一天、`Pacific/Auckland` 讓 end 讀成後一天，讀回補正會把對的住宿改錯），讀每個命中的 notes；編號比對時去前後空白、不分大小寫。這個範圍只是第一輪：變更或取消通知可能把住宿移到範圍外，所以第一輪找不到時，先用歸檔狀態對到的事件，再把範圍放寬到通知所述日期的前後各一年；仍找不到就問，變更與取消通知永遠不建事件。命中的事件若旅館或日期差太多、可能是重用編號的另一筆住宿，先給使用者看再更新。事件的來源行記著它反映的那封訊息的日期，更早的訊息視為已被取代，不改事件。沒有標記但看起來是同一筆住宿的手建事件，用對照表加一次詢問採納，使用者的舊 notes 放在標記行之下。

選訂房編號而不選「旅館名加日期」，是因為改日期的訂單會被日期鍵當成新住宿；編號跨改期、改房、部分取消都不變。選單行標記而不是兩行（會議模組有 umbrella / session 兩種事件）是因為這裡只有一種事件。

### 未確認的住宿：暫時鍵，之後升級

沒有訂房編號時標記行寫 `lodging-module: unconfirmed | <旅館名> | <入住日>`，標題前加「（未確認）」。確認信到時，先用編號找；找不到才以旅館名加重疊的住宿（使用者猜的日期可能不同）找未確認的候選，走會議模組既有的對照表（舊事件 → 新訂單，問一次）；使用者說好才改寫標記為編號、去掉前綴。理由：不另做一套升級流程，沿用已有的「不確定就列表問一次」。輸入沒有明確的日期**與**地點時不建，在回報說明缺什麼並向使用者要（沒有人能回答時列為待處理）。

### 取消：先問，說好才刪；不改成「（已取消）」

取消通知到時，用編號找出事件（取消通知常只帶編號，第一輪找不到就用放寬的搜尋），列出「這個事件，因為這封取消通知的這幾行」，問一次；使用者說好才用 `delete_event` 刪除，回報點名被刪的事件。這個 yes 必須是對這個事件、這封通知、這一次執行問的問題的回答，先前對別的通知給的 yes 不算；沒有人能回答的執行（排程或無人值守）只在報告列為待處理、什麼都不刪、停下來。`archive-event` 與 `/quick-event` 的 `allowed-tools` 不列 `delete_event`（預先核准會拿掉權限提示這道保險），所以那兩個入口刪除時 harness 會再問一次；`calendar-management` 有列，那裡模組自己的 yes 是唯一的關卡。不用「（已取消）」前綴有兩個理由：#342 的 Expected 要求移除，且一筆過時的住宿在日曆上正是這個功能要防的失敗。為什麼一定要問：`delete_event` 只在 server 執行期間可 undo，行程資料不該靠這個保險。為什麼這不違反會議模組的「不自動刪除」：那條規則留在會議模組；刪除規則寫成共用規則（下一節），賦予「模組自己建立、經使用者同意」的事件，住宿模組採用它，會議模組沒有採用。

### 共用規則加四條（`event-modules.md` 的「Common to every module」）

1. 模組只能刪自己建立（靠標記認）的事件，只在使用者對這個事件、這一次執行問的問題說好之後（先前的 yes 不算；沒有人能回答就只列為待處理），且回報點名被刪的事件。該模組的契約必須自己宣告採用；沒宣告的模組（會議）仍然不刪。
2. 一則輸入同時符合多個模組的觸發條件時，每個模組只建自己的事件，日曆**各自**解析（一個模組的路由規則不影響另一個）。
3. 以某個識別碼（訂房編號）為鍵的來源，權威訊息是最新一則帶該識別碼的訊息；訊息順序不明時問。

加在共用規則而不是只寫在住宿契約，是因為第 2 條在第二個模組出現時才有意義，且索引現在對此沉默；第 1、3 條不是住宿獨有的。

### 變更逐欄套用、誰有資格改事件、取消紀錄

更新只覆寫變更通知寫明的欄位，其餘保留，只有明確撤回才移除，否則只改日期的通知會清掉地址與入住要求。只有訂房方陳述「已變更／已取消」的訊息才算通知；旅客回信、請求、「已收到申請」都不算。寄件網域（以可註冊網域比較，免費信箱一律問，轉寄信算原寄件者）與事件來源行不同，或事件來源行沒有寄件者（使用者陳述的事件），先給前後對照問一次，說好後把該訊息的寄件者寫進來源行，下一則才有東西可比；確認信、變更、取消三種都過這道檢查，同一個 Message-ID 重跑視為 unchanged 不問。這不是在恢復 §1 的 From 比對：From 本來就能偽造，真正要防的是「只依時間新舊選訊息」會把一則引用編號的回信當成權威。訊息的 `Date` 也是寄件者控制的，晚於收到時間的 `Date` 不信、改問。取消後在有狀態的入口（`archive-event`）留下取消紀錄（編號與取消訊息的日期時間），早於它的確認信不會把住宿建回來，晚於它的（重新確認）先問。每一則帶編號的訊息都先搜尋、找不到才放寬到所有日曆，在路由日曆以外找到的先問，因為備註裡的標記行可以被偽造，且不可寫的日曆不寫。

### 一單一事件，多房間寫 notes

不拆事件，因為鍵是訂房編號，拆開鍵就不唯一，改期時還要決定哪一個是對的。部分取消只更新 notes（房間列表與金額）並以剩下的房間重算起訖，各房入住夜數不同時，事件涵蓋最早入住到最晚退房，notes 逐房寫明、回報說明夜數不同，不問也不拆（問了不論答案都不改變動作，只是打擾）。

### 沒訂房的夜晚：只在回報說

只有輸入或使用者的話給了行程的起訖時才說（「5/3 回程前一晚沒有住宿」），不建事件，因為日曆事件會變成待辦的雜訊，且鍵難定。

### 與 `archive-event` 的邊界

跟會議議程同一個寫法，作為 `event-source-archiving` 的 ADDED requirement：`archive-event` 仍是入口，保留來源行（寄件人、日期、主旨、Message-ID）與 `state/archives.json` 的寫入（來源識別碼對到住宿事件），但訂房確認信由模組取代它的第 1 節（權威時間）、第 2 節的建立或更新選擇、與第 3 節的估計行（住宿沒有估計的結束，退房日缺就問）。會議模組的 umbrella 查找與標記行不適用於住宿：狀態對到的事件，只有 notes 含 `lodging-module:` 標記行才算模組事件，否則是手建事件、經對照表與 yes 才採納。`archive-event` SKILL.md 為此有自己的一段，不借用會議那一段：§1 的寄件者加可解析時間規則被取代（變更通知可能來自別的地址、取消通知常沒有時間），權威訊息按訊息自己的 Date 取最新一則帶該編號的；state 用 `<message-id>#lodging:<reservation>` 為鍵，以免與同一來源的會議 umbrella 互蓋，且只當提示，找事件靠編號。理由：`archive-event` 以原始通知的 Message-ID 為鍵，變更與取消通知是不同的信、不同的 Message-ID，鍵必須是訂房編號。

## Implementation Contract

- **Behavior**: 見 `specs/lodging-module/spec.md`。一封訂房確認信經任一入口進來，建出一個全天事件、標記含訂房編號、notes 的順序如版面；再來一封改期通知，更新同一事件；再來取消通知，列出事件並問，說好才刪。
- **Interface / data shape**: 一份契約檔 `plugin/rules/modules/lodging.md`；標記行 `lodging-module: <編號>` 或 `lodging-module: unconfirmed | <旅館名> | <入住日>`；設定鍵 `lodging_module: off`；沒有新的 MCP tool、沒有 Swift 變更。
- **Failure modes**: 缺入住日或退房日 → 問，不猜；找不到事件的取消通知 → 回報「找不到對應事件」，不建、不刪；同一編號有多個事件 → 全部列出並問；`delete_event` 失敗 → 回報，事件維持原樣。
- **Acceptance criteria**: `spectra validate add-lodging-module` 與 `spectra analyze` 無 Critical 與 Warning；契約檔、spec、design、proposal 對標記行、版面欄位順序、取消流程的文字一致；在名稱含 `#342` 的拋棄式日曆上實測：建、改期、取消各一次，讀回確認起訖與標記，結束後依 id 刪除日曆並用 `list_calendars` 確認清乾淨。
- **Scope boundaries**: 在範圍內——契約檔、索引、共用規則、`archive-event` 的 ADDED requirement、CHANGELOG；不在範圍內——#341 的自動檢查、Swift、提醒、拆事件、旅館以外的類別。

## Risks / Trade-offs

- 判斷「這是不是訂房確認信」「幾間房」「哪一則最新」是模型判斷；確認信格式千差萬別，契約只能列欄位與抄法，不能保證每家旅館都抄得全。
- 取消先問會多一個互動；換來的是不會在使用者不知情時刪行程。若之後使用者覺得煩，可以另開 issue 加「直接刪」的設定，現在不做。
- 刪除規則是共用規則的新能力，會議模組沒採用；兩個模組在「能不能刪」上不同，是刻意的，不是不一致。
- 全天事件的結束日讀法依事件當下是否已是全天而異（2026-10-29 單一裝置實測，會議總覽的實測只涵蓋 create 那一側，update 側與定時轉全天是本變更量到的，追蹤於 #364）；契約因此每次寫入日期後都讀回。若旅館與 host 跨日期線，邊界以 host 時區解讀，這一點沿用會議模組的實測，這裡不另做。
