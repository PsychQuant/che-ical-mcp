# Changelog — che-ical-mcp plugin

All notable changes to the `che-ical-mcp` Claude Code plugin are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> The plugin version tracks the `CheICalMCP` binary version (the wrapper auto-downloads
> the matching GitHub Release). Entries below are the plugin-facing condensation that also
> appears in the **Changelog** section of [`README.md`](README.md); the binary's full,
> categorized changelog lives in the repository root [`CHANGELOG.md`](../CHANGELOG.md).
> Entries marked *plugin shell only* / *documentation only* / *metadata only* shipped no
> binary change.

## [Unreleased]

- **Trip-folder reminder and the `itinerary-check` skill** (#341) — *plugin shell only*: work on a trip records its facts where that work lives (a receipt in the mail archive, a revised program in the conference folder), and nothing told the calendar. Now a `SessionStart` hook records when the session started, and a `Stop` hook, in a folder with a **project-level** `.claude/.ical/config.yaml` (the nearest one, found as #337 does; the user-level `~/.claude/.ical/config.yaml` does not count), lists the files changed there since then and, when there are any, adds one `additionalContext` asking Claude to run the new `itinerary-check` skill. Once per **interactive** session: a headless run (`claude -p`, the Agent SDK, an unattended or scheduled session) gets no reminder, because its extra turn would replace the run's result; this is judged, at start and again at stop, from `CLAUDE_CODE_ENTRYPOINT` (only `cli` counts as interactive; any other value, an IDE or desktop entrypoint included until one is confirmed, counts as headless) and `CLAUDE_CODE_SESSION_ATTENDED` (`cli` alone does not mean a person is there: background jobs report `cli` too and are excluded only by `CLAUDE_CODE_SESSION_ATTENDED=0`), which Claude Code sets for hooks but does not document, so an interactive session resumed with `claude -p --resume` gets no reminder either. Never a block (exit 0 always, never 2: the wrapper loads the module inside a catch-all, so even an unreadable module ends in 0; silent when `stop_hook_active`, and when `python3` is the macOS stub without the Command Line Tools); `.git/`, `.claude/`, `.DS_Store` and symlinks are skipped; only names and modification times are read; the walk counts directories and files, stops after 2 s or 50 000 entries, checked between entries (a single listing that hangs is ended by the hook's 10 s timeout), and names at most 20 files as display names (control and format characters removed, long names cut), with their count, which the reminder calls data, not paths to open; the exact paths are stored in `${CLAUDE_PLUGIN_DATA}/itinerary-sessions/` and the skill reads them with `bin/itinerary-changed.sh`. Each directory is read one entry at a time inside the bounds, and a walk the hook timeout kills also pauses the next ones. Every directory below the trip folder is opened through the one above it without following a symlink and listed by that descriptor, so a directory swapped for a symlink during the walk is not followed. The trip folder is the working directory's own ancestor, so a symlinked `.claude` does not move it; when the working directory was entered through a symlink and the config sits above the link's target, it is the ancestor of the working directory's real path, where the config was found. The skill compares a file's real path with the trip folder's own real path, both resolved, so a trip folder under a symlinked `~/Dropbox` has its files read. The skill gives an all-clear (no trip facts, or the calendar matches) only after a full check: the walk complete, every changed path stored and printed, every printed path read; otherwise it says what it checked and how many files it did not store or read. The hook runs python with `exec`, so a timeout ends the walk itself. The reminder asks Claude to run the skill for the changed files (or to tell you it can) and never invites a dismissal from the file names: only the skill's full check reports that there are no trip facts. Changes from other sources (Dropbox and other sync clients, an editor's temporary files, another session in the same folder) count too; skip them with `itinerary_ignore`. A file copied with its old modification time kept is not seen. After a walk that stopped early, was killed, or took 1 s or more, and found nothing, that session does not walk the folder again for 5 minutes; each further such walk in the session doubles the pause, up to 1 hour (another session in the same folder walks it at once). A folder the walk cannot open or list, or whose listing fails partway, makes the stored list incomplete (a file or folder that is gone by then does not), the changes found elsewhere are kept, the 2 s bound is checked before each folder too, and the reminder says so, so the skill gives no all-clear. The 30-day cleanup spares every record of the current session, so a session resumed after 30 days is not reminded twice, unless another session's start pruned its records first. The hook writes only under `${CLAUDE_PLUGIN_DATA}`, and only when it lies under the same root the helper accepts (below): from that root down, every directory, the data directory and the sessions directory included, is opened without following a symlink, and every record is created, read, written and removed through that descriptor, so a symlinked data directory or ancestor stops it before it writes anything; a record with another hard link is refused before it is truncated, and the helper refuses such a list too; the helper prints the paths as UTF-8, and never prints a name holding a control or format character (a newline, a bidi override, a zero-width space) or one that is not text: it counts it as unreadable, prints `complete` only as a bool and `total` only as a non-negative number, counts a stored path that is absolute or has an empty, `.` or `..` component as unreadable, refuses a trip folder that is not absolute and an empty `HOME`, accepts a data directory only under `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/plugins/data/` (at least one level down, no `.` or `..`), and opens every directory below that root and the list without following a symlink. A FIFO or other non-regular file at a record name is refused, so it cannot hold the hook. An inline `itinerary_ignore` list honours quotes (an escaped `\"` or `\\` inside double quotes and a doubled `''` inside single quotes are part of the pattern, in inline and block lists alike), a quote opens only at the start of a value (so `Bob's drafts/` needs none), a `#` inside quotes is not a comment, names and patterns are compared in Unicode NFC (a pattern typed as NFC matches a folder macOS stored as NFD), and only a pattern ending in `/` prunes a directory. If the helper exits non-zero, the skill reads no changed file, reports the helper's message and asks. The skill reads the trip folder's own config and `state/archives.json` through the trip folder's path even when `.claude` is a symlink, and stops to ask when a config applies but cannot be read. `${CLAUDE_PLUGIN_ROOT}` in the skill's `allowed-tools` is substituted by Claude Code in plugin skills, as in the body (skills documentation, 2026-11-09), so the two helpers are pre-approved as written; not yet seen in a live session. The session record lives in `${CLAUDE_PLUGIN_DATA}/itinerary-sessions/`. `itinerary-check` reads the changed files for trip facts (registration, payment, program, lodging, transport; not review, teaching or administrative deadlines), finds the trip's events by module marker, then `state/archives.json`, then name and date window, answers in one line when everything matches, and otherwise shows one table and changes nothing before the user's yes; a program revision goes through the conference module's partial correction and a stay through the lodging module, and the skill routes a change by whose event it is first (a conference or lodging marker goes to that module, anything else to `update_event`), a fact with no event by its kind (a new program to the conference module's full paste). On the itinerary-check path a module writes nothing (create, update, delete, read-back correction) before the user's yes on the skill's table. Its `allowed-tools` lists calendar read tools and two Bash commands, the config lookup and the changed-paths helper, with the plugin root quoted, and no `Read` (a read outside the working directory prompts as usual): those are pre-approved in the turn that reads the trip's files, so nothing that turn reads can run a write without a prompt from the skill's own grant. That list is not a check on writes, though, since your settings may allow them: the user's yes to the difference table is the only gate. **Upgrade effect: the reminder is on by default, so existing project-level configs start getting the reminder after this upgrade.** Put `itinerary_check: off` (or `no`, or `false`) in the config to turn it off, or `itinerary_ignore:` (a list of globs; one ending in `/`, such as `draft*/`, skips a matching directory at any depth, and a leading `/`, as in `/drafts/`, only at the top of the trip folder) to skip files. It sees that files changed, not that a trip fact changed, so a reminder can be for nothing; a fact that exists only outside the folder is not seen. Tests: `scripts/tests/itinerary-reminder-test.sh` (temp `HOME`, temp `CLAUDE_PLUGIN_DATA`, fictional trip folders; no calendar is read). Not verified: the reminder in a live Claude Code session (change task 1.2). **Known limit:** a session run as a Claude Code background job may get no reminder: such a session's processes have been seen with `CLAUDE_CODE_SESSION_ATTENDED=0` while a person was answering in it, and whether the main agent's Stop hook sees that value is not known yet (task 1.2 records it).

- **The lodging contract closes the follow-ups of PR #363's verify rounds** (#365) — *documentation only*: these are rules the model follows; no binary change. **Trust.** A forwarded message's sender and date shown only in its body are unverified, and the table shows the forwarding sender next to the claimed one. A message that reaches a stay only through `References` or `In-Reply-To` is asked about and never leads to a deletion. A marker line is no proof of who wrote it, so a hit outside the routed calendar is always asked about. Copied text is escaped for every module's marker prefix (`conference-` for the conference module's marker lines and block lines, `lodging-module`), in both contracts and in a new shared rule. Secrets (a closed list of kinds) stay out of the questions, the tables and the report too, and a value that may be one is left out. The check-in line is quoted as the sender's words. A cancellation record now holds the property and the stay's days, and counts only for the same number at the same property; a record from before this change matches on the number and asks. State keys percent-encode the number, so two numbers never share a key. **Every write from a mail to an existing stay asks once, with a before/after table; only a create applies without a question** (and asks too when the message's date is in the future, missing or cannot be ordered). The known sender, `Accepted senders:`, the free-mail list, DMARC and forwarding only set flags in the table: a forwarded mail and a planted `Authentication-Results` header could pass the earlier no-question confirmation and source-line paths, so they were removed. The first yes on an event the module did not write itself shows and resets its `Accepted senders:` line and source-line sender. A statement that finds a stay in another calendar asks before updating it. A partial room change or cancellation asks too. An older mail is never dropped for its age alone. A different booking number for the same place and nights is a possible match, not a second stay. The user's phone change survives every rewrite of the source line. A change notice, any confirmation that differs, a reminder that disagrees and a cancellation all ask. The flags are a closed list; only the topmost `Authentication-Results` header counts, and its pass is a hint. A newer identical mail changes nothing, the source line included. Accepted senders live on their own `Accepted senders:` line, and a copied subject cannot plant a field or end its quotation early. A phone change records its time, and every later date-moving mail asks. Reservation numbers normalise to one canonical string. A delete the user asked for leaves a `by_user` record that never supersedes a mail. A different spelling of the property is a possible match in the table, not a new stay. Nights covered only by some all-day event are still listed as not booked, with that event named. An event with two modules' markers is written by neither. The state file holds private trip data and belongs outside git. **Search and dedup.** "Overlapping dates" means sharing at least one night. A restated unconfirmed stay is found by property and shared nights, so moved dates no longer miss it, and the unconfirmed upgrade is reached from the hits the search already made. A user's "I changed it by phone" is a path of its own: a before/after table, one question, and the end-day rule. `calendar-management` changes or deletes a stay only through the module, and creates no event that carries a stay marker (a copy or a migration leaves the stay out and names it). A booking archived before the module and rescheduled by another message is also looked for on its previous dates. Nights without a booking name an all-day event without a marker that covers them. An event with the marker twice is never updated, adopted or deleted. A second cancellation notice is reported as already cancelled without a question, and one that meets a `by_user` record as already deleted by the user; a record or a `by_user` record silences a cancellation notice only on the same number, the same property and its days (a notice that states other days is shown with the record and asked about). Labelled lines are parsed only above the marker. A skipped create with the same number is `unchanged` only when nothing differs. A cancellation never adopts. A state entry that maps the reservation or the Message-ID to an event that no longer exists (a stay deleted by hand) asks before creating, and is pending when nobody can answer. The report lists, next to `created`, the flags the creating message would have had, and names an unconfirmed stay at the same property that shares no night with it. A stay with two numbers leaves one cancellation record per number; once the user answers that the second number is the same stay, the search and the state hint also match the `(also …)` number on the `Reservation:` line, and the entry point maps the message under that number too, so a later message under it finds the stay instead of creating a second one. The key of a delete the user asked for includes the deleted event's identifier, so two stays deleted by one request keep two records. The first yes on an event the module did not write itself resets the source line's sender; its date and Message-ID still follow the order of messages. Only a cancellation notice that carries the reservation number reaches the deletion question; one found only through its thread is listed. A reconfirmation after a cancellation record is pending when nobody can answer. **No create beside a stay at the same property.** Before every create (from a mail or a statement, also one that already asks), the module looks in every calendar, one year around the nights, for any event with a lodging marker line at the same property, an `unconfirmed` stay or one that also carries another module's marker included; any hit makes the create a possible-match question, and with nobody to answer nothing is created. The guard does not depend on reservation numbers, `(also …)` parts or state. The guard matches the property name or the street address, names the calendar of each row, and leaves out an event already answered for the same message (an answer for another message of the run does not carry over); a guest who returns to the same property within a year is asked each time; a stay spelled otherwise, at a different or missing address and sharing no night, is a stated known limit, next to a stay built by hand without a marker. The user's same-stay answer writes the `(also …)` part itself; the part is a list a later same-stay answer appends to, every later write keeps it, and a mail cannot plant one. An event that belongs to neither module gets no `(also …)` part: the user is asked to remove the extra marker. A deletion writes one cancellation record per number on the `Reservation:` line and per state entry that names the event, and a mail cancellation's key includes the deleted event's identifier. Deleting an `unconfirmed` stay leaves no record, so once no stay at that property remains nothing holds a later create of it. An entry point that keeps no state says that archiving the same confirmation again creates the stay again. The report names an unmarked all-day event that covers a created stay's nights. **Shared rules and documents.** "Nobody to ask" names a change from a mail. The conference spec gets a requirement for the shared rules it follows. The `archive-event` conference paragraph no longer takes a stay for a single event archived before the module. The contract points at the archived spec, which is the source for the facts both state. The title's night count is the span's. Not verified: the device walk of tasks 3.1 and 3.2 (needs the user present).

- **The conference contract closes the gaps an acceptance run found** (#351) — *plugin text only*: the five paths that had been checked only as text were run once on throwaway calendars with the repo-built binary, and the text is changed where the run and the text disagreed. The changed rules themselves were not run on a calendar, except the umbrella date write. The rules now: **a hand-built event is never adopted, renamed or written** (adoption is deferred from v1: review rounds 2 to 5 each found new holes in it). Find step 3 runs with no set, and with a set for the items and the umbrella it lacks; it takes events whose title holds the official or short name and timed events in a slot the set lacks, and leaves an event out only when every item it may be already has an event. Each item such an event may be gets one yes/no row, "hand-built event X found; create the item anyway?": yes creates the item beside it, no creates nothing and the row comes back on later pastes, unanswered it is pending. Create is not offered where `create_event` would skip or duplicate (the event has the item's title and covers its start, or an all-day event is titled with the official name exactly for the umbrella): the item is then kept and the event named. An item the set lacks, with nothing listed for it, is a "not in the set → create?" row, since a hand-deleted event looks the same as a new item. A program whose official and short names both changed asks, in the mapping table's one question, whether it renames a same-day set that overlaps it (the same title after the short name, or two sessions at the same date and time; an opening, a closing, a break, a meal (懇親会 included), an award ceremony or a general assembly does not count), naming every such set; the answer names one set or none. When the run's calendar holds more than one candidate or same-day set, that choice is asked alone first, and the pairing, the hand-built search and the item rows are worked out for the chosen set and asked only after it (with nobody to answer, nothing is written). The cross-calendar search runs when the routed calendar has no exact set; its one question, asked only when it finds a set in another calendar, only chooses the run's calendar (use can be chosen for one set), and when the chosen set then turns out not to be this program's, the whole existing-set flow runs again in the routed calendar, and the first table's answers are asked again, before a new set is built there. After a set-level no or a rename answered none in the same calendar, the hand-built search runs again for the full program. A correction that would move or rename an old event onto a slot a hand-built event holds asks "update anyway?"; that row and the hand-built rows each need their own answer, not a plain yes, and so does an old event's row that names a hand-built event. An umbrella that would be updated onto days a hand-built all-day event covers asks the same, and a hand-built event found there stays listed although the set has an umbrella. A timed hand-built event with the conference's name that runs over more than one of its days is listed for the umbrella, which then asks "create anyway?". A one-set rename question is answered only by naming that set or a yes to it, never by a plain yes to the table; that answer does not answer the set's "not in the set" or hand-built rows. A candidate set's umbrella left as it is after an "update anyway?" no stays under the old marker, and the report says so. A slot another set's module event holds is not offered for creation; the item is kept and the report names that event. Only rows answered explicitly are written; a row left unanswered is pending; while a set-level row is unanswered every other row waits; with nobody to answer, a table with a set-level row creates nothing and the question comes back on later pastes. Pairing takes exact matches out first, then pairs by the same title, the same title after each side's short name, then the same date and start. An exact set's umbrella with other dates is updated, and every umbrella date write is read back; the dates of an all-day event are read without `display_timezone`. The clash check runs after the table, against every calendar (`check_conflicts` without `calendar_name`), skipping the old events that rows answered yes map to program items (an old event whose correction was answered no is still checked); a clash with a hand-built event the table lists is reported on a line of its own. Known limits: an old set that fits none of the three kinds is not asked about and the program is created as a new set (the official name changed, and either the first day changed too, or no session title overlaps and fewer than two non-common sessions overlap by date and time); a row answered no comes back on every later paste (a remembered decline is a v2 follow-up).

- **The wrapper's sidecar records the release it installed, not the pinned version** (#483) — *plugin shell only*: when the tag `plugin.json` pins had no release yet, the wrapper fell back to `releases/latest` and still wrote the pin into `~/bin/.CheICalMCP.version`, so once the pinned release appeared the sidecar already matched and it was never downloaded (v1.23.0: machines that updated the plugin between 2026-11-01 and 2026-11-08 kept v1.22.0). The wrapper now decides from what the binary reports (`CheICalMCP --version`), not from the sidecar: it downloads when the binary is missing, cannot report a version, or reports one older than the pin, so a machine already left in that state gets the pinned release on its next spawn. **A binary newer than the pin** (from `--self-update` or `make install`) is kept, with one stderr line saying so. The sidecar records what the installed binary reports. The last release downloaded is recorded in `~/bin/.CheICalMCP.release`. A release whose binary reports another version than its tag, or none, is not downloaded again while that record still describes what is installed. "Describes" means one of three things: the installed binary reports a version not older than the one the asset reported, or the version kept over an asset that reports none, or it is that asset itself (same `cksum`). A failed download, or a failed `mv` over the installed binary, writes no record and is retried on the next spawn, which prints the error again. **Delete that file to make the wrapper try the release again.** Right before installing, the wrapper probes the installed binary again. An asset that reports no version, or a version not newer than what is installed at that moment, never replaces a binary that reports a version, even one that `make install` or `--self-update` put there during the download. An HTTP error body is never installed (`curl -f`). Only one spawn downloads at a time. The lock is `~/bin/.CheICalMCP.lock`, holding the downloader's pid, and each download goes into its own temp file. A spawn that finds the lock held by a live process waits up to 5 s, then runs the installed binary. A lock whose process is gone is taken over at once. A TERM during the download (the client giving up) ends the wrapper at once and removes its lock and temp file. Temp files left by a killed run are removed by the next download. **While the pinned release does not exist yet**, each spawn makes up to two small GitHub API calls (the pinned tag, then latest), each giving up after 5 s, and downloads nothing when latest is not newer than what is installed. Tests: `scripts/tests/plugin-wrapper-test.sh` (stubbed `curl`, temp `HOME`). A machine in the bad state gets the fix only through a plugin version whose release exists.

- **The lodging and conference contracts pass the check-out day (the day after the last day) on create and on update** (#364): the server now reads a date-only all-day end the same way on both tools. Their description of `create_event` `skipped` changes too: a timed session is skipped only by a same-titled timed event, and an all-day umbrella or stay only by a same-titled all-day event starting on the same day. The lodging module no longer passes the last night when it updates a stay that is already all-day. Its read-back after every dates write stays, and with a server older than #364 it corrects the one extra night. Needs the binary that ships #364.

## [1.23.0] - 2026-11-01

- **The skill, `/check-tcc` and the plugin docs describe the status-aware self-disclaim rule** (#343): the server keeps the host's grant only when it has full access to both Calendar and Reminders, or when a policy restricts the host (#367); any other host, Claude Code included, re-execs onto CheICalMCP's own grant, which `--setup` creates. After upgrading, run `~/bin/CheICalMCP --setup` once in the foreground if CheICalMCP is not granted yet, then restart the client. `--print-tcc-path` says when a host's grant is kept on purpose; the banner and the access-denied message give the same steps. Not verified: the natural re-exec under a session Claude Code starts through `ClaudeCode.app`.

- **Lodging module (#342)** — *plugin shell only*: a hotel booking confirmation, change notice or cancellation notice (or a stay the user states with check-in and check-out dates and a place) becomes **one** all-day event over the nights stayed, with the street address in `location`, the property name, nights and check-out day in the title, and the check-in requirement, reservation number, plan, amount, cancellation terms and source in the notes (never a card number). The event is keyed by the **reservation number** in a `lodging-module: <number>` marker line, so a change of dates updates it. A stay with no confirmation is created only from stated dates and a place, titled `（未確認）`. A cancellation shows the event and **asks before deleting it**. Nights without a booking are reported, never created. `lodging_module: off` in `.claude/.ical/config.yaml` turns it off. Shared rules for every module gain four lines: a module deletes only an event it created or adopted and only after the user's yes to that question in that run (the conference module still deletes nothing), several matching modules each build their own events and resolve their own calendar (the conference contract now leaves a stay to the lodging module), a module does nothing on a point where nobody can answer and lists it as pending, and for a source keyed by an identifier the latest message carrying it is authoritative. Measured on one device (iCloud, host +09:00; Google and Exchange not measured): a date-only `end_time` is the exclusive check-out day on `create_event` and when an update turns a timed event into an all-day one, but includes that day on `update_event` of an event that is already all-day, so the contract passes the last night then and always reads the event back and corrects it with one more update when it differs; the conference umbrella is exposed to the same difference on its updates (#364). Secrets (card numbers, PINs, door or login codes) are never copied into the notes, a cancellation is deleted only after a yes given to that question in that run (an unattended run lists it as pending), and a change or cancellation notice that finds no event asks instead of creating. A change notice is applied field by field (a notice that only moves the dates keeps the address and the check-in requirement); only a message from the booking party that states the change counts as a notice, and a different sender domain asks first; every message with a reservation number, and any message in a thread that already produced a stay, goes to the module; every message with a reservation number is searched in the routed calendar and then in all calendars, and a hit in another calendar asks before it is updated; a cancellation leaves a record so an old confirmation does not bring the stay back (the latest record wins); a `create_event` that the server answers with `skipped` is never reported as created: the module compares the markers and, for another reservation with the same title and dates, creates again with the reservation number added to the title; `archive-event` §2 reads the mapped event's notes (all calendars, a range covering the event; not found counts as unknown) before updating it and never updates a stay as a single event, with the lodging module off too, while a flight or meeting in the same thread is still archived; a hotel message that does not repeat the number is matched through the thread's state entry; copied text cannot become a labelled line (a `conference-module` marker keeps the conference module's own rule). A stay's dates are always read without `display_timezone` (measured: a zone west of the host reads the start a day early, one east reads the end a day late); the thread's first Message-ID is not used for a stay, and any message carrying a known reservation number goes to the module, so a traveler's reply cannot be written into the stay by the single-event steps. `archive-event` has its own stay paragraph: the latest booking-party message carrying the reservation number is authoritative (the sender-and-time rule is replaced), and the stay is stored in `state/archives.json` under `<message-id>#lodging:<reservation>` with its reservation number and, after a cancellation, `cancelled_at`, so it does not overwrite a conference umbrella from the same message; a booking archived before the module (bare key) is offered for adoption. Not verified: the full device flow of create, change notice, cancellation and the unconfirmed-stay upgrade through the entry points; only the date behavior was measured.

## [1.21.0] - 2026-10-27

- **Conference module (#338)** — *plugin shell only*: a conference program (one named occasion on consecutive days with at least two separately scheduled timed items; not a single meeting's agenda) becomes one multi-day all-day umbrella event (official name, venue, day-by-day overview in notes; start and end given as dates, because an all-day event is read in the host's zone) plus one timed event per item in the conference's time zone, each created with `create_event` (`create_events_batch` cannot set reminders); sessions in the same slot in different rooms become one event with the rooms in notes, and your own talk is its own event; sessions you did not register for are created with the title prefixed `（未報名）`. Every event's notes carry two marker lines (`conference-module: <name> | <first day>`, `conference-module-item: …`); text you write below them is kept on every update. Re-pasting or correcting a program finds the set by those lines and updates it; sessions match by title and start time, so a changed title or start time, and any hand-built event without the marker, is shown in a mapping table for one confirmation; nothing the module did not create is written to without that confirmation, and nothing is deleted. Attended sessions get a reminder 15 minutes before and your own talk 60 and 15 minutes before (none on unregistered sessions; the module adds none to the umbrella, though your calendar's own all-day alert may apply); reminders are set on creation and when registration changes, so ones you edit survive a re-paste. The calendar is resolved once through routing (#337) for the whole program. `conference_module: off` in `.claude/.ical/config.yaml` turns it off. Contract: `rules/event-modules.md`, `rules/modules/conference.md`; `archive-event`, `/quick-event` and `calendar-management` point to it (a program archived from a thread maps its Message-ID to the umbrella in `state/archives.json`). Session times are local times plus `timezone`; a single-day input that would trigger asks once whether you want a program or one event (unless you called it a conference); updates carry the conference's zone too; a message that corrects only some items is applied to the existing set. `/quick-event` now pre-approves the read-only `search_events` and `list_events` for the module's dedup; its updates still ask. No binary change.

- **Per-folder calendar routing (#337)** — *plugin shell only*: a folder's `.claude/.ical/config.yaml` can route events to calendars by kind with a `calendar_routing` block (`kind`, `calendar`, non-empty `includes`, optional `source`). The config is the nearest one walking up from the working directory (closest wins, never merged; the walk stops at a git repository boundary or `$HOME`), then `~/.claude/.ical/config.yaml`. `archive-event`, `/quick-event` and `calendar-management` resolve the calendar through one shared rule, `rules/calendar-routing.md`, and every creation reports `Routed to <calendar> by rule '<kind>' from <config path>` or why it was not routed. An event that matches no rule keeps today's calendar choice; one that matches two rules asks you. `default_calendar` keeps its meaning (`archive-event` only, not a routing fallback), and a config with only `default_calendar` behaves as before. New helper `bin/find-ical-config.sh` with shell tests in `bin/tests/`. No binary change.

- **Undo of a whole-series delete restores the series' exceptions inside the scan window (#285)**: an occurrence deleted on its own earlier stays deleted, one edited on its own comes back as a separate one-off event; the series' first occurrence is always kept from the rule, and exceptions outside the window still come back from the rules; the undo text says which. Binary change; the plugin shell is unchanged.

## [1.20.0] - 2026-10-10

- **BREAKING (behavior) — a date-only reminder is overdue only once its day has ended (#297)**: `is_overdue` and `filter: "overdue"` in `list_reminders` read a date-only due as a day in the host time zone, not as 00:00, so a reminder due today is not overdue at any time today; `sort: "due_date"` puts it before the timed dues of its day; its `due_date` / `due_date_local` (also in `search_reminders`) print 00:00 of that day in the host time zone, and a start stored as 00:00 without a zone reads as a day in `start` (`time: null`).
- **A date-only create reports `date_sync`; a vanished due reads `aligned: false` (#301)**: a bare-date `create_reminder`, and each date-only row of `create_reminders_batch`, re-reads the saved reminder and returns `date_sync` like `update_reminder` (a timed create is not re-read, #308); `update_reminder` now returns `aligned: false`, where it used to leave `aligned` out, when a written due reads back missing. A skipped duplicate reports a match of the request's own kind, so a bare date with an exact date-only duplicate carries no "has a time" note.
- **Reminder and event dates are read and written in the Gregorian calendar (#299)**, not the host's region calendar (Buddhist, ROC, Japanese, Islamic), so such a host no longer writes or reads the wrong year; the bare-date duplicate check compares days, not instants.
- **BREAKING (behavior) — a bare `YYYY-MM-DD` `due_date` makes a date-only reminder (#267)** on `create_reminder`, `create_reminders_batch` and `update_reminder`, instead of 00:00 with a time; on update the start date becomes that day and absolute-date alarms are removed (Reminders.app would keep showing an alarm's time), relative and location alarms stay, and `date_sync` counts what was removed. A date-only create writes the start as the same day too. The create duplicate check keeps its rule (a bare date compares as 00:00 of that day); it now reads dates in the Gregorian calendar, with a date-only value at 00:00 in the host zone, so on a non-Gregorian host calendar, or for a stored date-only due that carries a time zone, its result can differ from before.
- **`update_reminder` `realign_to_due` (#235)**: puts the start date and absolute-date alarms onto the due date (new or current) whatever it moved by, anchored on the earliest absolute-date alarm, the date Reminders.app displays; refused with `clear_due_date` or when there is no due date at all. `date_sync.aligned` reports whether the start date and that alarm agree with the due date, and a start date EventKit creates during the write reads `set` instead of `absent`.
- **A timed due date written to a floating reminder keeps its explicit time zone (#237)**, so iCloud Web no longer shows it shifted by the UTC offset.
- **BREAKING (behavior) — `undo` / `redo` refuse to overwrite a change a person made after the operation (#236)**: undo re-reads the item and refuses, writing nothing and keeping the entry, when a field it would overwrite or delete was changed since (fields already changed back do not count; a create-undo compares everything the item holds, and for a recurring event created here also occurrences edited on its own, within four years). An alarm sound and coordinates added to a place are not treated as edits and are overwritten. The error names the fields; whoever made the change decides whether to change it back and retry, or to drop the entry with `undo` + `discard_id` (the only choice for occurrences edited on their own, a series whose occurrences could not be checked, and a series whose rule was shortened by an update or delete of an occurrence and the following ones). An occurrence counts as edited when it differs from the series in any compared field (alarms, time zone and place included); one back at the series' values does not. A missing item's error now names it and `discard_id`.
- **BREAKING (behavior) — undo of an `update_event` that touched a recurring event is refused (#236)**: one occurrence (also a detached occurrence by its own id), span "future", span "all", or rules added or removed. Nothing is written, the message says to revert the change in Calendar if wanted, and the entry is discarded so earlier entries stay undoable. An update or move recorded on a one-off event is refused the same way if the event repeats by the time of the undo. Undo of a one-off event's update is otherwise unchanged; a safe recurring restore is #263.
- **Undo of a `span: "all"` `update_event` no longer deletes the series (#262)**: it removed every occurrence but a detached copy of the first (data loss, in v1.19.0 and earlier); it is now refused.
- **`list_reminders` and `search_reminders` report the start date and time-based alarms (#231)**: new `start` field (in the `due` shape) and `alarms` (relative `minutes_before`, or absolute `absolute_date`); location alarms stay in `location_trigger`.
- **Undo keeps what it used to flatten (#228, #230, #242, #244, #245)**: reminder undo keeps location alarms, recurrence and URL and restores into the list the reminder was in; event undo keeps absolute-date, location and email alarms and availability; undo of a one-occurrence delete no longer recreates the whole series beside the surviving one; `copy_event` keeps those alarm kinds too.
- **`delete_reminders_batch` and `cleanup_completed_reminders` record undo (#243)**, and a batch undo that cannot finish no longer restores the same items twice (#248).
- **BREAKING (behavior) — `redo` of anything but a completion writes nothing and answers `success: false` (#247)**, instead of moving the record back onto the undo stack.
- **Event tools given a reminder's identifier answer not found instead of ending the server (#260)**, which also lost its undo history.
