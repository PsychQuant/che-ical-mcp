# Unblocking undo history

A missing event or reminder does not prove permanent deletion. Normal undo retains transient failures so a source or permission problem can be repaired and retried.

Undo also refuses, and keeps the record, when the item was changed after the operation in a way the undo would overwrite or delete (#236): the error names the changed fields. Whoever made the change decides: ask the user whether to change it back and undo again, or to give up that undo and discard the record as below. Three create-undo refusals leave only the choice whether to discard: occurrences of a series edited on their own (`modified_occurrences`), which cannot be put back into the series; a series whose occurrences could not be checked (`unchecked_occurrences`, the series has no identifier or calendar); and a series whose rule was shortened (`recurrence`; an update or delete of an occurrence and the following ones does this), whose cut-off part cannot be put back. Any other change of the rule can be changed back, so it is an ordinary refusal.

Six refusals discard the record themselves, so older records stay reachable:
1. a recurring reminder completion whose identifier now resolves to another occurrence (#204);
2. a completion recorded without an occurrence snapshot when the reminder still repeats with the opposite completion;
3. any `update_event` that touched a recurring event (one occurrence, also a detached occurrence addressed by its own id, span "future" or "all", or rules added or removed), listed as `Updated recurring event: <title> (undo not available)` and never undone;
4. an `update_event` or a one-off `move_events_batch` move recorded on a one-off event when that event repeats, or is an edited occurrence, by the time of the undo; a move of an item that was already an edited occurrence is always refused this way. Revert a move by moving the event back;
5. a `delete_event` with span "future" that did not start at the series' first occurrence and remove it all (it started at a later occurrence, the last one included, or the id named an edited occurrence), listed as `Deleted occurrences of recurring event: <title> (undo not available)`, and a `delete_events_batch` that holds such a delete, refused before any of its events is restored (#244). Restore the occurrences in Calendar if they should come back. A delete from the first occurrence lands here too when the lookup after it fails (#288): whether the series is gone cannot be told then, so it is recorded this way rather than as a whole series that an undo could create a second time. The response does not say so, and in a `delete_events_batch` it costs the undo of the whole batch, the other rows included.
6. a `create_calendar`, `update_calendar` or `delete_calendar` (#273), listed as `Created calendar: <title> (undo not available)`, `Updated calendar: <title before the update> (undo not available)` or `Deleted calendar: <title> (undo not available)` (`create_calendar` that found an existing calendar of that title records nothing). Undo never reverts a calendar operation: deleting a created calendar would delete what was added to it since, and a deleted calendar cannot be recreated with its events or reminders. The entry is recorded only so that undo after a calendar operation does not revert an older, unrelated operation in its place; the refusal writes nothing and does not name the calendar, and once the entry is discarded the next undo reverts the operation recorded before it. Revert the operation in Calendar (or with `update_calendar`, `create_calendar`, or `delete_calendar` with `require_empty: true`) if it should be reverted; deleting a calendar together with what it holds is for the user to decide. `create_calendar` creates in the default account and returns an existing calendar of the same title instead of a new one.

For 3 and 4, revert the change in Calendar if it should be reverted; a safe restore is tracked in #263. Undo of a delete of one occurrence (span "this") is not refused: it restores the occurrence as a one-off event, because EventKit cannot put an occurrence back into its series, with an absolute-date alarm of the series moved to its start (#244). Undo of a whole-series delete (span "future" that started at the series' first occurrence and removed it all, or span "all") recreates the series from its rules and then restores its exceptions inside the checked window (#285): the delete lists the occurrences that exist over one window of at most four years (1460 days, one EventKit query), before it removes anything. Since #319 the window is placed around the time of the delete: it starts three years (1094 days) before the delete, or one day before the first occurrence when that is later, and it is moved earlier when the rule ends sooner, so that it ends one day after the end of the rule; for a rule that ends after a count of occurrences, that end is the latest slot the count can reach (a weekly count on several weekdays counts its weeks), which only moves the window earlier and does not cut it, and a count whose end cannot be shown (a filter, a day after the 28th) is placed as open-ended. A count, known or not, whose window around the delete starts after its first occurrence is also listed over the window from its first occurrence (the window before #319, which listed every count as open-ended): the record holds both windows, and undo applies the exceptions inside either, so every exception inside the window before #319 is restored as it was before #319 (unless the store no longer lists that early history; then only the window around the delete is kept). So the window reaches at least a year past the delete, a series begun within about three years of the delete keeps the window from its first occurrence that it had before, and a series that ended long before the delete is checked toward its end: one with an end date over its last four years up to that date, a count with a known bound from its first occurrence when it spans under four years and otherwise over the 1460 days before that bound, and a count around the delete and, when that starts after its first occurrence, from its first occurrence too. Before #319 it started at the first occurrence, so for a series begun more than about four years earlier it lay entirely in the past and the exceptions that mattered were never listed. Occurrences outside the window, before or after it, come back from the rules; the undo text gives the window's start and end to the minute (they fall at the time of day of the delete or of the first occurrence, not at midnight) and says on which side the series has occurrences outside it, or may have them after it (a count whose end is only bounded, or cannot be shown); undo removes the occurrences the series did not have, so one deleted on its own earlier stays deleted, and recreates each occurrence edited on its own as a separate one-off event that no longer belongs to the series. The undo text says how many of each. The series' first occurrence is never removed: if it was edited or deleted on its own it is kept from the rule and the text says so. Exceptions outside the window, a series whose exceptions could not be listed when it was deleted, and a first occurrence edited or deleted on its own (kept from the rule), and a record that did not match the recreated series (none of its exceptions is applied) come back from the rules alone, while an edited occurrence moved more than a year outside its slot's window is not restored and its slot counts as deleted, and the text says which. If restoring the exceptions fails part-way, the recreated series and the one-off events created so far are deleted again and the entry is kept for a retry; if that delete fails too, the error says so and the entry is dropped. `undo_history` lists such a record as `Deleted event: <title> (undo recreates the series and its exceptions within the checked window (from <start> up to <end>), or windows (from … up to …, and from … up to …) for a count whose window around the delete starts after its first occurrence: occurrences deleted on their own earlier stay deleted, edited ones come back as one-off events; not for a first occurrence edited or deleted on its own, one moved more than a year outside the checked window or windows, or a record that does not match the recreated series)` (a record whose exceptions could not be listed keeps `undo recreates the series from its rules: …`), and a `delete_events_batch` record that removed a series whole (span "future" starting at the series' first occurrence, or span "all"; it records a batch even for one event, while `delete_event` with span "all" records a single entry) as `Batch (<N> operations; undo recreates <K> series and its/their exceptions within the checked window or windows: …)` (`1 operation` for one); the delete of a one-off event stays `Deleted event: <title>`, and a batch without a series `Batch (<N> operations)`. A batch that holds, at any depth, a span "future" delete that undo does not restore (item 5 of the refusals above) is listed as `Batch (<N> operations; undo not available: a member deleted an occurrence and the following ones of a recurring event)`, whatever else it holds: its undo is refused before any of its events is restored. Undoing the record of an earlier delete of one occurrence afterwards writes nothing, and says so, when the restored series already holds that slot; where the exceptions were restored it writes the one-off, which is the right result (the series did not bring the slot back). Since #321 "the series" is the one the occurrence belonged to, or a series that an undo of its whole-series delete recreated (this server keeps that link in memory, as it keeps the history), matched by identifier, and "the slot" is the one the rule gave the occurrence (from the `/RID=` of an edited occurrence's identifier), so neither the title nor an edit before the delete decides it; the holders are listed a year on each side of the slot, so an occurrence of the series edited and moved to another day still holds it (one moved further is not seen); before, any recurring event with the same title at the same second held the slot, an unrelated series included. A record that does not say which series the occurrence belonged to writes the one-off and says it could not check (an occurrence's rule-less whole-series delete record too). An occurrence edited on its own before its delete whose slot the series holds again is held as the rules give it, so its edit did not come back, and the text says that instead of calling it restored (a visible duplicate can be deleted; a success that wrote nothing could not be noticed). The same check covers a split move's source and an occurrence edited on its own that a series delete removed by its own identifier beside its series (`delete_events_batch` with both ids): undo runs the series first, so that occurrence finds its slot held. If the series' member fails and is retried last, the occurrence runs first and is written, and a series then restored from its rules alone brings the slot back too. A series recreated in Calendar by hand is not linked, nor one whose identifier changes after its save (a sync, a move within a Google account, a span-future split): the occurrence is written beside it. Each such undo lists the calendar over two years around the slot; a large batch has not been timed.

Batch records (`delete_events_batch`, a series delete, `delete_reminders_batch`, `cleanup_completed_reminders`) are undone member by member (#248). Each such call is one entry however many items it held; like any new entry it clears the redo history, and only the newest 50 undo entries are kept, so a frequent scheduled cleanup pushes older entries out. Before the first write, the calendar (for a reminder, the list) each member goes back into is checked, once for the whole batch; a deleted occurrence goes back into its recorded calendar (#244). The check looks each one up as the restore does, by its recorded identifier (#208, #242): a calendar or list with the same name in another account does not count. A calendar or list that is there but read-only (a read-only shared or subscribed one) does not pass either. When one is missing or read-only, a refresh of the store is requested and the lists are read again before refusing. The refresh runs in the background, so that second read may not see it yet; every refused undo requests one again, so a later retry may find what this one did not (not checked on a device). A refused batch writes nothing and the record is kept whole: it is this check that refuses the whole batch. The error counts the items it stops, says what kind of calendar or list stops them and why ("2 events in a calendar that is not available: …"), naming the items (their titles shown and capped; a shared calendar's item titles may be set by its sharer) but no calendar, list or account (a shared calendar's title is set by someone else and an account name is often an e-mail address, #37), and says how many have their calendar or list in place; those can still fail at their own save. That holds for this refusal: an error a member raises during the writes is quoted in the part-way error with its own text, and #242's missing-list error names only the reminder, not the list or its account (#290), as #269's missing-calendar error for a single event undo names only the event. Giving up with discard_id drops every item of the entry, including those: a deleted calendar or list does not come back even if one with the same name is made, so for its items giving up is the only way on, and it costs the others too. A partial restore that keeps the rest is #287. A calendar that is only unavailable for now (an account still syncing) or whose access may change can be retried later. A batch that also holds a delete of an occurrence and the following ones is refused by that refusal instead (item 5 of the refusals above), and its record is discarded: that refusal is checked first. When a save still fails, the record is put back with only the members not yet restored, under the same id, so undo again never recreates the restored ones a second time. The failing member is placed to run last, so undo again restores the others first: each member restores one new item without reading another's result, a deleted occurrence too (it comes back as its own one-off event), so the order does not change what any of them restores. Every record kind says whether it may run last; the kinds no batch records (updates, moves, creates, completions) may not, and a batch holding one would keep its recorded order instead. That helps only when the failure is not the member's calendar or list: if that is now missing or read-only, the next undo's check refuses the whole batch before any write, and the only way on for the items not yet restored is to bring that calendar or list back or give up the rest with discard_id (#287). A member whose error is permanent would be dropped, and the members never attempted kept; with none left, the record discarded. One batch member's write can throw such an error since #285 (restoring a series' exceptions failed and deleting the recreated series again failed too: a retry would create a second series); that member is dropped, and the tool descriptions say so. The error names what the members it restored did not restore as they were (an occurrence's absolute-date alarm, a series recreated from its rules), and the retry's text names it only for the members it restores, so each is reported once. After a part-way failure the entry holds only the members left, so the retry's `Undone batch (N operations)` (`(1 operation)` for one), its `undo_history` description and the redo instruction after it count those members, not the original batch. When a reminder's save reports a failure, a new store looks the reminder up, as at every site that saves a new reminder (#261): found, the save counts as done and the member counts as restored, so a retry never recreates it; when compared fields differ from what was saved, the batch answer (or, part-way, the error) names those fields for that reminder ("Restored reminder '…' — the store holds a different due, title; check it.", one entry per such reminder with its own fields, the first five, then how many more), from the names the restore returns, never from its text; a nested batch would pass its reminders' names up (no tool records one today). Not found, it is removed from the store without committing; if that removal fails it stays pending, the next member's save can write it, and a retry can write a second copy. An event has no such check: one whose save reports a failure after the store took it is treated as not written, and a retry can write a second copy (not seen on a device). The partial-failure error names the item that failed (its recorded title, quotes replaced and capped, plus its recorded start, or a reminder's due date, when another item of the batch shares its title, #407) and says its restore may have left something written, so a retry can add a second copy: check first. When that item failed because its calendar or list was not found, which happens before anything is written, it says instead that a retry adds no copy of it. The same error answers when the only member left fails before anything is restored (#292): the record is kept whole, under the same id, and the error says no item is confirmed restored, then gives the member's own error last; it used to be that member's error alone. A batch's deleted events and occurrences report what their undo did as data too (#323): the batch answer (or, part-way, the error) totals the series restored with their exceptions (occurrences that stayed deleted, occurrences that came back as one-off events, first occurrences kept from the rule), counts the series restored from their rules alone, the series whose recorded exceptions did not match and the occurrences already restored by their series (nothing written), and names `absolute_alarms` only for an occurrence that came back as a one-off event.

Redo writes only completions again (#247). This is the design, not a gap (#295): redo does not replay a create, delete, update or move, because the tool that made it repeats it with its own checks, and a replay would need what undo has for its own writes (the post-state guards of #236, a rule for an item changed since the undo, a new undo entry, and the new identifier of a recreated item). For any other record on top of the redo history (a create, delete, update or move, or a batch of deletes), redo writes nothing, does not touch the undo history, and answers `success: false` with the tool that repeats the operation (for example `delete_event` after the undo of a delete). The instruction is returned once: the entry is then removed from the redo history, and the next redo applies to whatever is then on top of it (an older undone operation, which may itself be one that redo only answers). The entry never returns to the undo history, so the next undo goes on to the operation before it instead of undoing the same operation a second time (which recreated a deleted item twice).

A single undo whose calendar or reminder list is missing is refused and its record kept, without writing anything: for a reminder (#242, #290) the error names the reminder, and for an event (the undo of `delete_event`, one occurrence's delete, `update_event`, or a move, also a whole-series move through the stand-in; #269) it names the event; neither names the calendar, list or account. A move that fell back to a copy or split one occurrence out has its own record (#466); its restore of the source names the move and the calendar it was moved from, and says the copy stays in the calendar it was moved to, if it is still there, when the undo is given up. An event undo judges its calendar missing only after Calendar access is checked and the store's view is read once more after being marked stale, as the batch check does, so an access problem is reported as that, not as a deleted calendar; the re-read requests a background refresh and reads at once, so it can still see the old view, and a later undo may find what this one did not. The error says the calendar or list is not available (deleted, or its account turned off or still syncing), offers running undo again only when the record holds its identifier (an event recorded without a calendar, #286, gets "recorded without an identifier" and no retry), says what giving up loses, and asks to give up the undo with discard_id only if the user agrees.

A plain `copy_event` (without `delete_original`) records the copy as a created event (#273): undo deletes the copy through the create-undo check (#236), refused with the record kept when the copy was changed since. Before, it recorded nothing, so an undo after it reverted an older operation.

The undo of a move that fell back to a copy or split one occurrence out (#466) restores the source as the undo of a delete does, with the same calendar check and refusals (a split's source as one occurrence: a one-off event; a fallback copy's source as a one-off event), and only then looks at the copy. When an occurrence of the split's series (or of a series an undo recreated from it) already holds its original slot in its calendar (#285, by series and slot since #321), nothing is recreated and the copy is not looked up or removed: removing the copy could leave the occurrence nowhere. Otherwise it removes the copy when it is found under its recorded identifier, unchanged since the move in the fields the check of a created event's undo compares (#236), and without attendees (they are not compared, and removing the copy could send them a cancellation), and otherwise leaves it and says why (changed, with the fields; attendees; not found; recorded without an identifier; not checkable; or its removal failed). Only where the copy is known to be in the calendar it was moved to (its removal failed, it has attendees, or it changed in fields that leave out its calendar) does the answer say the event is now in both calendars; otherwise it says it may be. The check and the removal run on the server's actor with no other call of this server in between; a change another process saves in between is not excluded. A copy never stops the source from coming back. Once the source is back the entry is used up, whatever became of the copy, so running undo again undoes the operation before it. `undo_history` lists it as `Moved event: <title> (by copy: undo restores it in its original calendar and removes the copy if unchanged)`, or for a split `Moved occurrence of event: <title> (split out: undo restores it as a one-off event in its original calendar and removes the copy if unchanged; if its series there already holds its original slot, nothing is recreated and the copy stays)`, and redo writes nothing and names `move_events_batch`, warning that moving again after an undo that left the copy adds a second one. Before #466 this was a delete record of the source, and the copy always stayed.

To intentionally abandon the newest record, call undo_history, inspect the first entry, and pass its id to undo as discard_id. Example: `{"discard_id":"<id returned by undo_history>"}`. This removes only that current top record. It does not edit events/reminders and does not add a redo record; discarding history cannot be undone. Existing redo records are preserved.

The server rejects malformed IDs, stale IDs, an empty stack, and discard requests while undo/redo is running. Read undo_history again after a stale error; do not blindly reuse an ID. IDs are stable across a failed undo and expire when records are discarded, evicted or the process restarts. Event, reminder and batch records follow the same rule. The UUID selects a record; it does not grant additional access.
