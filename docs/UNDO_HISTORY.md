# Unblocking undo history

A missing event or reminder does not prove permanent deletion. Normal undo retains transient failures so a source or permission problem can be repaired and retried.

Undo also refuses, and keeps the record, when the item was changed after the operation in a way the undo would overwrite or delete (#236): the error names the changed fields. Whoever made the change decides: ask the user whether to change it back and undo again, or to give up that undo and discard the record as below. Three create-undo refusals leave only the choice whether to discard: occurrences of a series edited on their own (`modified_occurrences`), which cannot be put back into the series; a series whose occurrences could not be checked (`unchecked_occurrences`, the series has no identifier or calendar); and a series whose rule was shortened (`recurrence`; an update or delete of an occurrence and the following ones does this), whose cut-off part cannot be put back. Any other change of the rule can be changed back, so it is an ordinary refusal.

Five refusals discard the record themselves, so older records stay reachable:
1. a recurring reminder completion whose identifier now resolves to another occurrence (#204);
2. a completion recorded without an occurrence snapshot when the reminder still repeats with the opposite completion;
3. any `update_event` that touched a recurring event (one occurrence, also a detached occurrence addressed by its own id, span "future" or "all", or rules added or removed), listed as `Updated recurring event: <title> (undo not available)` and never undone;
4. an `update_event` or a one-off `move_events_batch` move recorded on a one-off event when that event repeats, or is an edited occurrence, by the time of the undo; a move of an item that was already an edited occurrence is always refused this way. Revert a move by moving the event back;
5. a `delete_event` with span "future" that did not start at the series' first occurrence and remove it all (it started at a later occurrence, the last one included, or the id named an edited occurrence), listed as `Deleted occurrences of recurring event: <title> (undo not available)`, and a `delete_events_batch` that holds such a delete, refused before any of its events is restored (#244). Restore the occurrences in Calendar if they should come back.

For 3 and 4, revert the change in Calendar if it should be reverted; a safe restore is tracked in #263. Undo of a delete of one occurrence (span "this") is not refused: it restores the occurrence as a one-off event, because EventKit cannot put an occurrence back into its series, with an absolute-date alarm of the series moved to its start (#244). Undo of a span "future" delete that started at the series' first occurrence and removed it all recreates the series from its rules: occurrences deleted or edited on their own before it come back as plain occurrences (#285).

Batch records (`delete_events_batch`, a series delete, `delete_reminders_batch`, `cleanup_completed_reminders`) are undone member by member (#248). Each such call is one entry however many items it held; like any new entry it clears the redo history, and only the newest 50 undo entries are kept, so a frequent scheduled cleanup pushes older entries out. Before the first write, the calendar (for a reminder, the list) each member goes back into is checked, once for the whole batch; a deleted occurrence goes back into its recorded calendar (#244). The check looks each one up as the restore does, by its recorded identifier (#208, #242): a calendar or list with the same name in another account does not count. A calendar or list that is there but read-only (a read-only shared or subscribed one) does not pass either. When one is missing or read-only, a refresh of the store is requested and the lists are read again before refusing. The refresh runs in the background, so that second read may not see it yet; every refused undo requests one again, so a later retry may find what this one did not (not checked on a device). A refused batch writes nothing and the record is kept whole: it is this check that refuses the whole batch. The error counts the items it stops, names the calendars or lists that stop them, and says how many have their calendar or list in place; those can still fail at their own save. Giving up with discard_id drops every item of the entry, including those: a deleted calendar or list does not come back even if one with the same name is made, so for its items giving up is the only way on, and it costs the others too. A partial restore that keeps the rest is #287. A calendar that is only unavailable for now (an account still syncing) or whose access may change can be retried later. A batch that also holds a delete of an occurrence and the following ones is refused by refusal 5 instead, and its record is discarded: that refusal is checked first. When a save still fails, the record is put back with only the members not yet restored, under the same id, so undo again never recreates the restored ones a second time. The failing member is placed to run last, so undo again restores the others first: each member restores one new item without reading another's result, a deleted occurrence too (it comes back as its own one-off event), so the order does not change what any of them restores. That helps only when the failure is not the member's calendar or list: if that is now missing or read-only, the next undo's check refuses the whole batch before any write, and the only way on for the items not yet restored is to bring that calendar or list back or give up the rest with discard_id (#287). A member whose error is permanent is dropped, and the members never attempted are kept; with none left, the record is discarded. The error names what the members it restored did not carry over (an occurrence's absolute-date alarm), and the retry's text names it only for the members it restores, so each loss is reported once. After a part-way failure the entry holds only the members left, so the retry's `Undone batch (N operations)`, its `undo_history` description and the redo instruction after it count those members, not the original batch. A save that reports a failure after the store took the item is treated as not written, so the retry recreates that item a second time; this was not seen on a device, and for a reminder PR #280 leaves such an item in place (its `committedThenThrew` outcome) while the error still reaches the batch.

Redo writes only completions again (#247). For any other record on top of the redo history (a create, delete, update or move, or a batch of deletes), redo writes nothing, does not touch the undo history, and answers `success: false` with the tool that repeats the operation (for example `delete_event` after the undo of a delete). The instruction is returned once: the entry is then removed from the redo history, and the next redo applies to whatever is then on top of it (an older undone operation, which may itself be one that redo only answers). The entry never returns to the undo history, so the next undo goes on to the operation before it instead of undoing the same operation a second time (which recreated a deleted item twice).

To intentionally abandon the newest record, call undo_history, inspect the first entry, and pass its id to undo as discard_id. Example: `{"discard_id":"<id returned by undo_history>"}`. This removes only that current top record. It does not edit events/reminders and does not add a redo record; discarding history cannot be undone. Existing redo records are preserved.

The server rejects malformed IDs, stale IDs, an empty stack, and discard requests while undo/redo is running. Read undo_history again after a stale error; do not blindly reuse an ID. IDs are stable across a failed undo and expire when records are discarded, evicted or the process restarts. Event, reminder and batch records follow the same rule. The UUID selects a record; it does not grant additional access.
